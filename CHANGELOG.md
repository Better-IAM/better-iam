- Key management (KMS): a new `keys` API group gives each tenant keys whose material never leaves the server. AES-256-GCM keys encrypt and decrypt up to 4 KiB, bound to an encryption context, and issue data keys for envelope encryption; `reEncrypt` moves ciphertexts between keys. ECDSA (P-256, P-384), Ed25519 and RSA keys sign and verify, RSA keys can also encrypt with OAEP, and HMAC keys compute and check MACs. `signJwt` and `verifyJwt` work with signing and MAC keys, and `publicKey` / `jwks` publish public keys for offline verification. Keys have aliases, tags, versions with on-demand and automatic rotation, disable/enable, and deletion after a 7 to 30 day waiting period. Policies authorize `iam:kms:*` actions on `iam/kms/{keyId}` with conditions on key tags, spec, aliases, encryption context and algorithm, and key grants delegate named operations to one identity, re-checked against the grantor's own access on every use. Alias names are authorized on `iam/kms/alias/{name}`, and `signJwt` exposes the token's `sub`, `iss` and `aud` to policies. Every call is audited without plaintexts, and plugins never see plaintexts or tokens. Material is sealed under the deployment secret and re-sealed by `iam.rotateSecrets()`. The scheduler job `iam.kms.maintain()` rotates keys, destroys deleted ones and removes lapsed grants. New errors: `KEY_STATE_INVALID`, `INVALID_CIPHERTEXT`, `KEY_MATERIAL_UNAVAILABLE`. Guide: `docs/key-management.md`.
- Private certificate authority: a new `pki` API group runs X.509 certificate authorities per tenant, for mutual TLS, internal HTTPS and workload identity. Roots and intermediates (path lengths, name constraints, CRL distribution points) sign with KMS keys pinned to one version. `issueCertificate` takes a PKCS#10 request (`createCertificateRequest` builds one without OpenSSL) and decides `iam:pki:issue` separately for every name on the certificate (`resource.name`, `resource.nameType`, validity, usage, key type), so policies can limit teams to their own DNS names. `requestCertificate` gives a service account, agent or person a SPIFFE X.509-SVID for its own identity. Revocation (a subordinate CA's included), cached signed CRLs served publicly through `iam.pki.crlResponse`, trust bundles, and `iam.pki.verify` for servers that terminate mutual TLS (it checks the stored chain, revocation and authority state, and returns the workload identity). New errors: `INVALID_CSR`, `NAME_NOT_PERMITTED`, `AUTHORITY_UNAVAILABLE`, `CERTIFICATE_INVALID`. Guide: `docs/private-ca.md`.
- Data protection by tokenization: a new `protection` API group replaces sensitive values with tokens. Profiles per data type (`card`, `ssn`, `email`, `phone`, `generic`) choose format-preserving tokens (a card token keeps its length and last four digits but never passes the Luhn check) or random `tok_` tokens, deterministic tokens for joins, a display mask and a retention. Values are validated, normalized, and encrypted with one data key per call wrapped under a tenant KMS key. `tokenize`, `detokenize` (with a required `purpose`, visible to policies as `resource.purpose`), `mask` and `deleteTokens` (by token, or by value through a keyed fingerprint, for erasure requests) are separate permissions on `iam/protection/{profile}`. The audit trail records counts and purposes, never values or tokens. `iam.protection.sweep()` enforces retention. Guide: `docs/data-protection.md`.
- Key management, private CA and data protection hardening (security reviews): keys a certificate authority or a data protection profile uses are managed by it (`managedBy`, `KEY_MANAGED` for direct KMS use); changing a key's tags or aliases can never give the caller a KMS action they are refused now; delegated agents use up one confirmation per KMS, CA or data protection call; refusals are audited with the profile and purpose. The CA decides canonical names (wildcards as `nameType: wildcard`), requires the common name among the alternative names, reserves SPIFFE identity paths for `requestCertificate`, caps SVIDs at a day and at the credential and identity lifetimes, keeps trust domains unique, enforces path lengths over the whole chain, revokes descendant authorities with their parent, bundles roots only, and `iam.pki.verify` requires `tenantId` and a live identity. Data protection masks never show more than half a value (except first six and last four digits of 15+ digit cards), mask styles are per data type and policies see the style used, letters and digits of every script are masked and replaced, text is NFC-normalized and control, bidi and unpaired-surrogate characters are refused, format-preserving `ssn`/`phone` profiles are deterministic, SSN tokens avoid ITIN ranges, tokens are unique per profile (hashed key), the lookup key is wrapped under the profile's KMS key, customer keys need the caller's own KMS permission on every call, `tokenize` no longer returns `created`, shortening retention needs `iam:protection:delete`, sweeps run in batches and are audited, profiles report `tokens`, and deleting a profile retires its key. Migration `0006_protection_indexes` indexes value fingerprints (SQLite and libSQL).
- Secrets vault: a new `vault` API group keeps each tenant's secrets under path-like names, authorized as `iam:vault:read|reveal|write|rotate|lease|manage` on `iam/vault/secrets/{name}`, with the secret's tags as policy attributes (`resource.tag.{key}`). Secrets are `text` or `json`, versioned with stage labels (`current`, `previous`, `pending`, custom), kept to `maxVersions`, and can be disabled or destroyed per version. Rotation stages a generated value (CSPRNG generators with charsets, exclusions and character classes), lets a deployment-configured rotator apply it to the system it unlocks, and promotes it; failures keep the pending value for an idempotent retry and are recorded redacted. Check-out policies hand shared privileged credentials out one holder at a time, for a limited time, with a reason, rotating them when they come back. Dynamic secrets mint a credential per caller through an engine (`vault.engines`) with renewable, revocable leases. Values are sealed with the deployment secret, bound to tenant, secret and version, or under a customer-managed KMS key (`kmsKey`), so disabling the key shreds them. Deletion has a 7 to 30 day recovery window. `accessLog` shows who used a secret. Server code reads secrets and resolves `vault://name#field` references through `iam.vault`, whose jobs `rotateDue`, `expireLeases` and `purgeDeleted` run the schedule. Values never leave through "view as" sessions. New errors: `SECRET_PENDING_DELETION`, `CHECKOUT_REQUIRED`, `SECRET_CHECKED_OUT`, `VERSION_DISABLED`, `VERSION_DESTROYED`, `ROTATION_FAILED`, `ENGINE_FAILED`. Guide: `docs/secrets-vault.md`.
- Data filtering (query planning): `iam.planResources` and the `filters` API group (`plan`, and `planFor` for an administrator's preview with `iam:policies:simulate`) answer "which resources of this type may the caller perform this action on?" as a filter over the resource's `id` and attributes, by partially evaluating the same grants, denies, boundaries, relationships, sessions and delegations a decision uses (`always`, `never`, or `conditional`). The planner, `planResources` in `@better-iam/core`, mirrors the engine exactly (a randomized differential test compares it with `evaluatePolicy` and with SQLite), and the filter compiles with `filterToSql` (PostgreSQL and SQLite, parameterized and NULL-safe), `filterToPrisma`, `filterToMongo`, `filterMatches` and `describeFilter`. The Express, Hono, Fastify, SvelteKit and React Router integrations gain `plan({ action, type })` on their per-request helpers, and the console a Data filters preview page. Prepared decisions expose their inputs read-only (`DecisionInputs`). New error: `UNSUPPORTED_FILTER`. Guide: `docs/data-filtering.md`.
- SSH certificate authority (`ssh` option): a new `ssh` API group makes Better IAM the certificate authority for your servers. People, service accounts and agents get short-lived OpenSSH user certificates (`issueCertificate`, CLI `ssh-cert`) naming one principal `{login}@{host}` per host and login their policies allow: `ssh:login` on `ssh-login/{host}/{login}` with the host's labels as attributes, and `ssh:port-forward`/`ssh:agent-forward`/`ssh:x11-forward` on `ssh-host/{host}`. Certificates live only as long as the session or API key that requested them and the time-limited grants (just-in-time activations, temporary bindings and memberships, access windows) that allowed them; agents acting for people get ten minutes. Tenant settings can require MFA, FIDO security keys (with `verify-required`) or source-address binding. Hosts enroll once with a join token (`enrollHost`, CLI `ssh-host-enroll`), get a host certificate, the trusted user authority, per-login principals files, a key revocation list and an sshd_config drop-in, and check in with a renewal token (`syncHost`, CLI `ssh-host-sync`) that can never move them to another key. The host authority only vouches for names the organization owns (single labels, private addresses, its verified domains, within `hostPatterns`), each unique to one host and within the administrator's own `iam/ssh/hosts/{name}` scope; host keys can never be authority keys or another host's key; members' clients trust it for the enrolled names only, and the public trust route lists no host names. Revocation is by two KRLs, `user` for sshd `RevokedKeys` and `host` for clients' `RevokedHostKeys`; `iam.ssh.sweep()` (CLI `ssh-sweep`) re-validates each certificate's own session and revokes those whose holder became inactive, whose session ended, or whose hosts, logins or forwarding policies no longer allow. Suspended organizations still publish revocations (all user certificates). Renewal tokens rotate with every renewed host certificate, public host routes and issuance are rate limited, and refused host calls are audited. Authorities rotate in two phases (pending, active, previous, retired), are sealed under the deployment secret and re-sealed by `iam.rotateSecrets()`. `whoCanLogin` reviews host access, and the platform root override never opens an organization's hosts. New errors: `SSH_NOT_CONFIGURED`, `SECURITY_KEY_REQUIRED`, `SOURCE_ADDRESS_UNKNOWN`, `TOO_MANY_HOSTS`, `ROOT_SSH_RESTRICTED`, `HOST_OUTSIDE_PATTERNS`, `HOST_NAME_TAKEN`, `HOST_KEY_IN_USE`, `HOST_KEY_CHANGED`. Guide: `docs/ssh-access.md`.
- LDAP directory gateway: the new `@better-iam/ldap` package (also `better-iam/ldap`) is a read-only LDAPv3 server (`createLdapServer({ iam, tls })`) so applications that only speak LDAP (VPNs, NAS devices, CI servers, wikis) look up people and groups and check passwords against Better IAM. Each organization publishes its directory under its own base DN with the new `ldap` API group (`getSettings`, `updateSettings`, `directory`; permissions `iam:ldap:read`, `iam:ldap:manage`): people under `ou=people` (`uid` as email, local part or ID), groups as `groupOfNames` with `member`/`memberOf`, optionally service accounts, and only the identity attributes it selects. People bind with their password as a Better IAM sign-in (rate limits, lockouts, IP rules and alerts apply; people who use MFA append their current code), exactly one attempt per bind; service accounts bind with an API key. Binds without TLS are refused except from loopback, names with empty passwords are refused, and searches are authorized as the bound account: the whole directory with `iam:ldap:read` (audited as `ldap:directory:read`), otherwise only its own entry. Search (all RFC 4515 filters, paged results), compare and WhoAmI are supported; writes are refused. New error: `LDAP_BASE_TAKEN`. Guide: `docs/ldap.md`.
- Verifiable credentials (`verifiableCredentials` option): every organization issues SD-JWT VCs (IETF SD-JWT-based Verifiable Credentials, RFC 9901 selective disclosure) that people keep in digital wallets. Credential types (`iam:vc:manage`) map account data to claims: email, name, organization, teams, department, declared identity attributes, static values, each selectively disclosable unless marked otherwise. People get credentials for themselves where policies allow `vc:request` on `credential-type/{name}` (and MFA when a type requires it), through OpenID4VCI (`createOffer` returns an `openid-credential-offer://` link with a pre-authorized code and optional PIN, served by issuer endpoints mounted at `{basePath}/vc/{tenantId}` with `/.well-known` metadata, token, nonce and credential endpoints) or directly with `request`; administrators offer them to others (`iam:vc:issue`). Credentials are bound to a holder key proven with an `openid4vci-proof+jwt` over a single-use nonce. Revocation and suspension use an IETF Token Status List with random, never-reused indexes, served as `application/statuslist+jwt`; holders can revoke their own, and `iam.verifiableCredentials.sweep()` revokes those of people who left or may no longer request them. Self-service credentials end with the time-limited grant that allows `vc:request` (expiring bindings and memberships, just-in-time activations, access windows) or the role session they came from, and delegated agent sessions cannot obtain them. `verify` (public) and `iam.verifiableCredentials.verify` check signature, disclosures, key binding (audience and nonce, both required, freshness, `sd_hash`) and status. Proof nonces are signed rather than stored, public issuer endpoints only read, wrong wallet PINs and refused redemptions are audited as denied `vc:offer:redeem`, and a type's `vct` may not claim another organization's issuer. Issuer ES256 keys are sealed under the deployment secret and rotate with `rotateKey`/`retireKey`. `issueSdJwt`, `presentSdJwt`, `verifySdJwt`, `signStatusList`, `readStatusList` and `verifyHolderProof` are exported for wallets and verifiers. New errors: `TYPE_DISABLED`, `IDENTITY_INACTIVE`, `CLAIM_UNAVAILABLE`, `INVALID_PROOF`, `INVALID_NONCE`, `ACCESS_EXPIRING`. Guide: `docs/verifiable-credentials.md`.
- Privacy and consent management: a new `privacy` API group records each tenant's processing purposes with their legal basis (consent opt-in or opt-out, legitimate interests, contract, legal obligation, vital interests, public task), data categories and retention, and each person's decision on them, made by the person (`mine`, `decide`), recorded by the application for its own customers (`record`, `importDecisions`, or `iam.privacy.record` without a credential) and checked with `check`, `filterSubjects`, `audience` or `iam.privacy.check`. Purposes have versions that ask for consent again and optional consent lifetimes. Every decision appends to an append-only history and returns an HMAC-signed consent receipt that `verifyReceipt` checks, across secret rotations. Policies see `principal.consents`, the purposes that may be processed for the person now. Data-subject requests (access, portability, erasure, rectification, restriction, objection, opt-out) are filed by the person, by staff with a verification record, or through an optional public form confirmed by email (`submitPublic`, `confirmPublic`); requests known only by an email address are linked to their subject (`linkRequest`) or declined as `no-data`. They run on GDPR, UK GDPR, CCPA, LGPD and PIPEDA deadlines with one extension where the law allows, and fulfilment builds exports (downloadable for a limited time, then swept), erases accounts and privacy records (an erased application subject stays suppressed as `ERASED`), restricts processing, or withdraws consents. Legal holds refuse erasure and every deletion of the person's account. `iam.privacy.sendDeadlineReminders()` reminds handlers of due and overdue requests and lapses unconfirmed ones. Authorized as `iam:privacy:read|manage|record|check|handle`; audited as `privacy:*` events; emails `privacy-request-verify`, `privacy-request-received`, `privacy-request-update` and `privacy-request-due` with the `links.privacy` builder. Console pages: Organization › Privacy and Home › Your privacy. New errors: `LEGAL_HOLD`, `CONFIRMATION_INVALID`. Guide: `docs/privacy.md`.
- Security fixes from a review of authentication, sessions, temporary credentials and the framework integrations:
  - SvelteKit `protect` rules now match the path SvelteKit actually routes (percent-decoded, and the matched route id for `reroute` aliases); before, `/%61dmin` skipped a `/admin` rule. Remote functions still need their own guards.
  - A password alone can no longer enroll an authenticator over an existing factor: when a passkey is registered, the MFA challenge answers `enrollmentRequired: false` (new `authenticatorEnrolled` field) and `beginMfa`/`confirmMfa` from the login challenge are refused with `MFA_REQUIRED`.
  - NestJS: `@Public()` no longer turns `@Authorize`, `@RequireMfa`, `@Credentials` or `@RequireClaims` into no-ops for anonymous or invalid credentials (401 instead); CSRF checks also cover GraphQL over HTTP; the assertion guard accepts a lowercase `bearer` scheme.
  - `roles.assume` refuses delegated agent sessions (`CREDENTIAL_CHAINING_DISABLED`), so an agent cannot mint a role JWT that outlives its delegation.
  - An identity past its `expiresAt` is refused at sign-in and on every session use in the authentication service itself, not only in authorization decisions.
  - `startPasswordless` replaces earlier codes and links for the destination; the first emailed sign-in to a self-registered account whose address was never verified ends its sessions and removes the password chosen at sign-up (new `Identity.unprovenPassword`, cleared by verifying the address or resetting the password; the owner sets a password through reset), so an account registered in someone else's name cannot be kept by its registrant; verify-email and password-reset links only work for the address they were sent to; emailed MFA codes are stored with a keyed digest; new authenticator secrets are 160 bits.
  - `reauthenticate` refuses an expired password (`PASSWORD_EXPIRED`) and honours `emailPassword: false`.
  - Impersonation sessions also end when the administrator's session idles out (the administrator's tenant idle timeout), when the tenant turns `allowImpersonation` off, or when the member becomes an owner or root administrator.
  - Lowering `sessionLifetimeMs` or `trustedDeviceDays` now also shortens sessions and remembered devices issued under the longer value. Network blocks also judge the address presenting a user session, and `bindSessionsToIp` also applies when a user session is the source of a role session.
  - Passkey sign-in with an email answers an unknown address, or one without passkeys, with the same shape of options as a real account, so it no longer reveals which accounts exist.
  - Assertions: scoped credentials (API keys with scopes, role sessions with a session policy) are refused like scoped session tokens, and only the canonical spelling of a signature verifies (server and `@better-iam/next` edge verifier).
  - Web-identity trusts: a `StringLike` pin on `token.sub` may use a wildcard only after two complete segments (`repo:acme/*` is accepted; `repo:*`, which admits every repository on the platform, and `repo:acme*`, which also admits `acme-evil`, are refused with `WEAK_TRUST_CONDITIONS`). Existing trusts are not re-validated: review them with `trust.list`. With a recorded client address, `sts.assumeRoleWithWebIdentity` counts `maxExchangesPerWindow` per trust and address (ceiling: ten budgets per trust), so anyone posting junk tokens to a public trust id can no longer block the real workload.
  - Delegation tokens never carry a scope that a deny among the person's grants could touch, including denies whose author's authority was revoked (these still apply to decisions).
  - Sealed values require a 128-bit GCM tag and a 96-bit IV; delegation-token and agent-card verifiers fail closed on a NaN or out-of-range clock tolerance; web-identity replay records are kept for the largest possible clock tolerance.
  - `Origin: null` is refused by the middleware and Next.js CSRF checks (it equals the `.origin` of trusted entries such as `capacitor://localhost`); `auth/confirmMfa` is pinned to the organization address like other sign-in calls; the Fastify and h3 fallback paths cap request bodies at 2 MiB; the Next edge middleware treats only `/api/iam` and `/api/iam/*` as the IAM API.
  - Sign-in notices summarize the User-Agent ("Chrome on Windows", new `describeUserAgent`) instead of quoting attacker-chosen text, email subjects are kept on one line, and display names have control characters replaced at creation.
- Security fixes from a review of authorization and the management API (each covered by `tests/security-*.test.ts`):
  - "View as" sessions: every check an operation makes on the side (may this role be granted, may this group be changed) now needs the impersonating administrator's rights too, not only the first one. No grant authority can be used while impersonating (`IMPERSONATION_RESTRICTED`), and view-as sessions can neither decide access requests nor change or remove bindings the member issued. Before, support staff could "view as" a broader administrator to create accounts with that administrator's roles or approve their own requests.
  - Policy matching: a pattern's `*` now also matches a literal `*` in the value, so a Deny on `file/shared/*` covers `file/shared/*x`. `?` is one character for astral characters on every path. Evaluation has a per-call work budget and refuses with reason `evaluation-limit` past it; `*`-only globs match by native substring search. One crafted `policies.test` call could block the server for seconds.
  - Denies outlive their author: when the authority behind a binding, role or attached policy is revoked (or its administrator offboarded), what it granted lapses and what it denied still applies. An editor can no longer remove or change a deny statement that another authority relies on (it attached the policy, bound the role, or its role inherits it): `PROTECTED_RESOURCE`, unless root.
  - Separation-of-duties rules follow role inheritance, and `roles.update` is checked like other granting operations.
  - Tenant-defined mode: a type only a tenant registered answers from its registry for its own `{type}:{verb}` actions; the application's actions on an undeclared type always go to `resolveResource`, so an organization cannot register `document` and pass checks on another organization's documents.
  - A principal of another tenant is refused before any resource or action is looked up, and the refusal is recorded in its own tenant (metadata `targetTenantId`) instead of the target's audit chain and webhooks. `authorize` returns a denial instead of `NOT_FOUND`/`RESOURCE_MISMATCH` for such callers.
  - `audit.verify` (and `verifyAuditChain` with a `head`) checks the whole stored chain: new failures `missing-prefix` (oldest events deleted without an `audit:prune` checkpoint) and `unchained` (an event inserted without chain fields); deleting every event fails the head check. Startup backfill chains only tenants without a chain yet.
  - Teams: moving a team, or opening an admins-only team to its maintainers, needs grant authority over what the teams hold; the maintainer path no longer overrides an explicit deny. Onboarding completion groups, group-to-team sync, team leave (when a team carries a deny) and maintainer standing through admins-only teams are re-checked against grant authority.
  - Access packages: `extend` and membership hand-over only lengthen what the package still bundles, automatic grants run the enforced access invariants, and `autoAssign.warnings` flags rules on facts other administrators control.
  - Identities and tenants: non-owners cannot disable, expire or delete owners; administrators cannot edit their own attributes, manager or expiry, and setting attributes or a manager at creation needs `iam:identities:update`; invitations are re-checked against the inviter at redemption; child tenants inherit the stricter of their parent's plan limits; subtree webhooks and the root tenant's sign-in policy, sessions and network blocks are root's; scoped API keys only issue keys within their scopes; demoting an owner revokes the owner grant authority.
  - Billing: plan prices apply only to usage inside the subscription and trials once per account and plan; seat recording uses internal keys callers cannot claim; sub-accounts inherit contract terms; usage cannot be attributed to platform identities or teams; payment terms and built-in meter keys are the platform's; CSV exports neutralize formulas.
  - Also: plugin endpoints can name the record they act on (`PluginEndpoint.resource`), so per-record policies apply; resource IDs cannot contain `*` or `?`; `resources.list` and `relationships.list` leave out records a policy keeps from the caller; approvers can shorten but not lengthen an activation; role mining is linear on crafted inputs; certification auto-close acts only for a creator still in good standing; analysis suppressions need a current finding.
- Identity lifecycle workflows (joiner, mover, leaver): a new `workflows` API group runs steps for each person a trigger fires for. Triggers are `joiner` (people who join after the workflow is enabled, or everyone with `includeExisting`), `mover` (watched attributes or `managerId` changed, against a baseline taken when the workflow starts), `leaver` (an active person was disabled), `date` (days before or after `createdAt`, `expiresAt` or an ISO date attribute such as `startDate`; a moved date fires again) and `manual`. A scope in the access-package rule language picks the people. Steps add to and remove from groups (`remove-from-all-groups` leaves team and package memberships alone), assign and revoke packages (rule-made assignments stay with their rule), send emails with placeholders (`workflow-message`) to the person, their manager, or addresses of members and verified domains only, sign people out, disable, enable, set attributes and expiry, delete (last step only), emit `workflow:event` for webhooks, and wait up to five times. A run keeps the steps it started with and the rights of the owner who approved them (the workflow's owner when it started, or whoever retried it), re-checked at every step with the owner's MFA state (`OWNER_INACTIVE` when the owner is gone); `update` with `activeRuns: 'cancel'` stops runs in progress. Steps never strip or edit owners or root administrators (`PROTECTED_RESOURCE`), and nobody changes their own account through a workflow they own, start or retry. A daily brake (`maxRunsPerDay`, 25 when a step takes access away, else 200) starts runs up to the day's allowance, holds the rest, and records `workflow:brake`. `preview` shows who is in scope, who would start and upcoming dates; `run`, `retryRun`, `cancelRun` and `evaluate` handle runs by hand, and the readers show names only to callers with `iam:identities:read`. `iam.workflows.runDue()` (every few minutes) and `iam.workflows.subscribe()` (with `iam.dispatchAuditHooks()`; `iam.workflows.idle()` waits for its background evaluations) run them; finished runs are swept after 180 days. - Shared Signals receiver: Better IAM now receives OpenID Shared Signals (SSF 1.0 with CAEP and RISC) from upstream identity providers. A new `signals` API group registers each organization's transmitters as signal sources (`createSource`, `listSources`, `getSource`, `updateSource`, `deleteSource`, `rotatePushToken`; at most 20 per organization, one per issuer). A source has an issuer with up to 5 aliases, accepted audiences, static public keys, a key URL or SSF discovery (`/.well-known/ssf-configuration`, then the legacy RISC document), an algorithm allowlist (never HMAC or `none`), push or poll delivery, subject mapping, and an action per event type. Events arrive by RFC 8935 push at `{signals.pushPath}/{sourceId}` (default `/api/iam/signals/push/{sourceId}`: `application/secevent+jwt`, an optional bearer token shown once and stored hashed, 64 KiB bodies, rate limited per source, 202 or `{ err, description }` with 400, 401, 404, 413, 415, 429 and 503 while keys cannot be fetched) or by RFC 8936 poll through the new scheduler job `iam.signals.poll()` (acknowledgements only after the event is stored, sent with the next request; `setErrs` for refused events; up to five requests per source and run; the poll token sealed with the deployment secret and re-sealed by `iam.rotateSecrets()`). `iam.signals.receive(sourceId, set)` hands in SETs from custom transports, and `signals.poll` polls one source on demand. Each SET is checked for size (16 KiB), compact JWS form, no key headers (`jwk`, `jku`, `x5u`, `x5c`) or `crit`, the allowed algorithm, `typ` `secevent+jwt` (per-source `requireTyp: false` for legacy Google RISC), signature, issuer, audience, `iat` within seven days, one event, no `nonce` and a consistent subject, then deduplicated per organization on issuer and `jti`. Service accounts, agents and deleted identities never match. The only direct action is `revoke-sessions` (every session except API keys) for the event types a source chooses, never against root administrators from other organizations. Everything is audited under names the transmitter does not publish, so nothing echoes back upstream: `signal:received` (actor `signal:{sourceId}`, with `sourceId`, `eventType`, `jti`, `status`, `identityId`, `reasonAdmin`, `currentLevel` and `credentialType` for threat detection), `signal:revoke-sessions`, `signal:source-create|update|delete|rotate` and `signal:reprocess`.
