# Architecture

The pure core defines policies and shared types. SQL adapters implement `IamStore`. Authentication and protocol packages operate on that contract. The server composes authentication, authorization, provisioning, and transport. The client contains only fetch-based transport and type inference. The umbrella package re-exports packages without eagerly importing protocol implementations.

## Public surfaces

`betterIam(options)` exposes `api`, `authorize`, `authorizeMany`, `listAccessible`, `require`, `handler`, `nodeHandler`, `events`, `initialize`, and trusted deployment/integration helpers. `api.auth` contains end-user authentication operations. Other API groups are `tenants`, `identities`, `groups`, `policies`, `roles`, `bindings`, `authorities`, `actions`, `resourceTypes`, `resources`, `relationships`, `serviceAccounts`, `credentials`, `trust`, `links`, `root`, `accessRequests`, `webhooks`, `audit`, and `assertions`.

Temporary credentials add the `sts` group (`getSessionToken`, `getCallerIdentity`, and the public `assumeRoleWithWebIdentity`) and the `oidcProviders` group, and, when `sts.jwt` is configured, `iam.sessionTokens` (`issuer`, `jwks()`, `verify()`) plus the `GET {basePath}/.well-known/jwks.json` route. The runtime-neutral verifier for other services is the `@better-iam/server/session-tokens` subpath (`better-iam/session-tokens`). See [temporary credentials](temporary-credentials.md).

Modules reach each other through the context at call time (`ctx.decisions.decide(...)`), which keeps them free of import cycles and lets each be read on its own. The authentication package follows the same idea: `service/base.ts` holds configuration and the session core, and `sessions.ts`, `account.ts`, `passwordless.ts`, `mfa.ts`, and `passkeys.ts` each extend the previous class with one feature; `outbox.ts` and `rate-limit.ts` are plain modules. The SCIM package separates its filter grammar, discovery documents, provisioning logic, and HTTP handler, and the OAuth package separates the provider adapter from the provider service.

Provisioning calls take `(credential, input)`. A credential contains request headers or a bearer token (an opaque bearer token or an IAM-signed session JWT, always backed by a stored session row), never caller-supplied identity claims. Direct calls and HTTP enter the same operation service, resolve current identity/session records, enforce authorization, mutate state, and append an audit event in one serialized transaction. Four operations are public because they precede a credential: `tenants.lookup` (alias discovery), `domains.discover` (email-domain discovery), `tenants.acceptInvitation`, and `identities.acceptInvitation`. A fifth, `sts.assumeRoleWithWebIdentity`, takes an external OIDC token as its only credential and is rate limited per trust before any lookup.

`iam.auth` exposes low-level authentication primitives needed by trusted integrations. `iam.store`, `bootstrap`, `recoverRoot`, `assertionKey`, and `protocolHost` are deployment/server capabilities. Do not expose them through application RPC reflection. The HTTP router explicitly excludes them.

## Identity and hierarchy

Every identity belongs to a tenant. Its normalized email is unique within that tenant; another tenant may have an entirely separate identity with the same email. Credentials, external-provider subjects, MFA, recovery challenges, and sessions remain tenant-scoped. A tenant is the equivalent of an AWS account: many people sign in to it, each with their own identity, credentials, and role bindings.

A tenant may carry a globally unique `slug`. `tenants.lookup({ slug })` resolves an active tenant without a credential so login screens can ask for an organization alias instead of a tenant ID; suspended, pending, and deleted tenants are not resolvable. Slugs are claimed in the same transaction as the tenant (`tenants.create`, `bootstrap`) or changed with `tenants.setSlug`, and are released when the tenant is purged.

Organizations can also be found by email. `domains.add({ tenantId, domain })` (`iam:domains:create`) claims a domain and returns a TXT record (`_better-iam-challenge.{domain}` = `better-iam-verification={token}`); `domains.verify` (`iam:domains:update`) looks the record up — before the transaction opens, through `domains.resolveTxt` (default `node:dns/promises`) — and marks the domain verified when the joined TXT value matches. A verified domain belongs to exactly one tenant (a global `domainOwners` record keyed by the domain), several tenants may hold pending claims, and consumer mailbox providers are refused (`domains.blockedDomains` replaces the default list). `domains.discover({ email })` is public home-realm discovery: it returns the active owning tenant with its alias, accepted sign-in methods, and MFA requirement, and answers 404 for unknown, pending, released, or inactive domains alike. `domains.list` and `domains.delete` complete the group; claims are removed when the tenant is purged. The console's organization picker offers "use your work email" on top of it.

People join an existing tenant in three ways: an administrator creates the identity directly (`identities.create`, or `identities.createMany` for up to 100 at once with attributes, roles, and groups applied under the caller's authority), self-registration when `signUpEnabled` is on, or a member invitation. `identities.invite` records the invited email with optional roles and groups, stores only a token hash, and enqueues a `member-invitation` delivery. `identities.acceptInvitation` is public: it creates the identity with a verified email, applies the bindings under the inviter's grant authority (re-validated at acceptance), records an audit event, and issues the first session subject to the tenant's MFA requirements.

Default hierarchy: `root → organization → project`, maximum depth eight. Configure `hierarchy.types` and `maxDepth` to change it. Runtime ancestry traversal rejects cycles. Creating an organization requires a currently authorized caller and a valid grant authority; its owner enrolls through a single-use invitation. No parent membership implicitly grants descendant access.

Suspension is inherited at authentication/authorization time and removes existing descendant sessions. Reactivation does not restore those sessions. Deletion tombstones the subtree, stamps retention timestamps, and revokes its sessions; audit records remain. Renaming requires recent authentication and `iam:tenants:update`. Moving a tenant additionally requires authority in the new parent, an active new-parent ancestry, permitted child types, and depth/cycle checks; delegation chains keep their original grant authorities. Tombstoned tenants are removed by the explicit `purgeDeleted` worker (default 30-day retention, also the `purge` CLI command); plugin-owned records are removed through plugin purge callbacks in the same transaction.

`identities.delete` (and `serviceAccounts.delete`) removes a person or service account under `iam:identities:delete` with recent authentication: sessions, API keys, factors, passkeys, bindings, group memberships, boundaries, external identity mappings, pending access requests, and links are removed or revoked in one transaction, delegated authorities the identity issued are revoked, and a tombstone with `status: 'deleted'`, no email, and no secrets remains so audit records stay resolvable. The last active owner and the last root administrator are protected. `identities.list` omits tombstones unless `includeDeleted` is set.

`identities.update` renames a member, replaces declared attributes, or changes the email (recent authentication; the address becomes unverified, sessions are revoked, and `identity:email-change` is audited). `identities.export` (recent authentication, `iam:identities:read` on the identity) returns a data-subject export: the public identity, sessions without token hashes, MFA enrolment and passkey identifiers, external provider subjects, effective bindings, groups, relationships, access requests, boundaries, grant authorities, links, SCIM links, and, when the caller also holds `iam:audit:read`, the audit events the identity performed. Each export is audited as `identity:export`. `identities.revokeSessions` ends one identity's sessions without disabling it, and `tenants.revokeSessions` ends every session in a tenant (keeping the caller's unless `includeSelf`); both require recent authentication and are audited. `identities.unlock` clears the rate-limit counters behind an identity's sign-in, recovery, and MFA flows (audited as `identity:unlock`); custom limiters opt in by implementing `reset`. `identities.requestPasswordReset` queues a password-reset email on a member's behalf, verified or not (audited as `identity:password-reset`). `identities.impersonate` opens a "view as" session for a member when the tenant policy allows it (`iam:identities:impersonate`, recent authentication, a reason; audited as `identity:impersonate`); see [security](security.md) for what such a session can and cannot do.

`tenantDefaults` in the options (`limits` and `authPolicy`, validated at construction) are stamped on every tenant that `tenants.create` creates, so a SaaS plan applies from the first sign-in. Owner and member invitations can be re-sent (`tenants.resendInvitation`, `identities.resendInvitation`): the token and lifetime are renewed and the earlier link stops working.

Root administrators may set plan `limits` on a tenant (`tenants.setLimits`, audited as `tenant:limits`): members, service accounts, groups, roles, policies, registered resources, and webhooks. Every creation path checks the limit inside its transaction and fails with `LIMIT_EXCEEDED`, including invitations accepted later, self-registration, federation, SCIM, and bulk creation; deleted tombstones do not count. `tenants.usage` reports the current counts, active sessions, and the limits for dashboards and metering.

A tenant may carry an `authPolicy` (`tenants.setAuthPolicy`): `requireMfa`, `allowedMethods` (`password`, `passwordless-email`, `passwordless-sms`, `passkey`, `federated`), `sessionLifetimeMs`, `sessionIdleTimeoutMs`, `maxAttempts` (authentication attempts per rate-limit window, never above the deployment's), `minPasswordLength` (12 to 128, checked wherever a password is set), `maxSessions` (concurrent user sessions per person; the oldest ends when one more is issued), `allowImpersonation` (lets administrators open "view as" sessions; off by default), `trustedDeviceDays` (how long "remember this device" may skip MFA; 0 turns it off for the tenant), `notifyNewSignIn` (email members about sign-ins from unfamiliar clients; overrides the deployment's `signInNotifications`), `allowedIpRanges` (networks sessions may be issued and used from; needs recorded client IPs), `mfaEmailCodes` (emailed one-time codes for members without an authenticator), and `bindSessionsToIp` (a session is usable only from the address it was issued from). The authentication service consults it when a sign-in starts, when a session is issued, and on every session validation; the policy can shorten but never extend the deployment's session limits, and it adds to (never replaces) the deployment's `requireMfa` callback. User sessions record their sign-in `method`.

Linked onboarding is opt-in. Existing identities require recent authentication to both accounts. The link never merges roles, credentials, or profiles. `links.list` returns the current identity's linked accounts for an account-switcher UI. Switching requires a valid link plus a recently authenticated target credential, then creates a fresh target session. This deliberately enforces target MFA without treating the link as a reusable bearer credential.

## Resource catalog

`permissions.resourceTypes` declares the product's resource types, their actions, attribute schemas, and relation names. Application-owned types are resolved by `resolveResource`; managed types are registered with IAM (`resources` group) and resolved from the `resources` collection. With `permissions.mode: 'tenant-defined'`, tenants register their own managed types and `{type}:{verb}` actions (`resourceTypes` and `actions` groups). Relationship tuples (`relationships` group) bind an identity or group to one resource under a declared relation and surface to policies as `resource.relations`. `permissions.identityAttributes` declares typed attributes administrators set on identities and service accounts, surfaced as `principal.{name}`. See [policies](policies.md) for validation and evaluation details.

## Plugins

A plugin is a plain object with an `id`. It may contribute `actions` and platform `resourceTypes` (validated like the product's own, and a name declared twice is rejected at construction), HTTP `endpoints` that run inside a transaction with the authorized principal and may queue deliveries through `deliver`, `hooks.beforeOperation`/`afterOperation` that run inside every `operation` transaction (before the mutation and after it, before the audit record; throwing aborts the operation), `resolveContext` for trusted evaluation context, `afterAudit` for committed events, `migrate`, and `purge`. `@better-iam/projects` is the reference implementation.

## Federation composition

Protocol packages take `iam.protocolHost` callbacks and their explicit configuration. Create a protocol service and call `iam.useProtocol(service)` to mount it. Standard protocol handlers use Request/Response; the OAuth issuer uses Node's request/response interface and must run through `iam.nodeHandler`.

Federation maps `(tenant, provider, issuer, subject)` to an identity. Unmapped verified email claims may provision a new account, but an existing email collision returns `ACCOUNT_LINK_REQUIRED`; applications must complete an explicit verified linking flow. No email-only association is performed.

## Data and consistency

Both adapters use a versioned `iam_records` table with collection, ID, tenant ID, natural key, and JSON data. Composite database constraints enforce scoped uniqueness; the `tenantAliases` collection uses the alias as its record ID so the primary key enforces global uniqueness. Services enforce cross-record references under transaction isolation. Additional collections represent accounts, sessions, hierarchy, policy versions, authorities, trust, invitations, resource types, resources, relationships, challenges, outbox, audit chain heads (`auditChains`, keyed by tenant ID), and protocol artifacts. Web-identity federation adds `oidcProviders` (unique per tenant by `issuer:{issuer}`) and `webIdentityReplays` (redeemed-token keys, primary key only, swept through the collection-wide `expiresAt` index); role sessions and session tokens are ordinary `sessions` rows found through the indexed `roleId` and `identityId`.

Transactions serialize writes and relevant reads. SQLite uses an immediate writer lock; PostgreSQL uses a transaction-scoped advisory lock. Every instance touching these tables must use the adapter contract. Raw SQL writes can violate service-level integrity and revocation guarantees.

No cross-request permission cache is used. Token validity and current role/policy state are checked on use. The one deliberate exception lives outside IAM: services that verify session JWTs offline with `createSessionTokenVerifier` trust the signature until `exp` and learn of revocation only then (IAM itself still checks the stored row); they call `sts.getCallerIdentity` when they need a live answer. Outbox delivery is at least once; callbacks must deduplicate by message ID. Events, plugin audit hooks, and webhook deliveries are queued inside the recording transaction and dispatched after it commits; see [events](events.md).
