# Security model

Trust boundaries are the application server, configured SQL adapter, cryptographic keys, protocol configuration, and application callbacks. Browser data, tenant administrators, external assertions, and bearer credentials are untrusted until validated. The server remains responsible for calling authorization before accessing product resources.

## Root and delegation

Root authority is a protected boolean capability on a root-tenant human identity, validated from current storage and requiring an MFA user session. A role called `root-admin`, a matching email, a linked account, or a JWT claim cannot confer it. Root overrides policy restrictions across tenants but not malformed input, expired credentials, CSRF, signature validation, or resource ownership validation. Cross-tenant root actions are recorded.

Bootstrap runs only against an uninitialized installation. Recovery creates a new root identity through a deployment-operator command and writes an audit event. Protect access to configuration, database credentials, and recovery execution as root-equivalent capabilities.

Member invitations store only a token hash, carry the inviter's grant authority, and re-validate that authority, the roles, and the groups when redeemed; a revoked authority or invitation makes the token useless. An inviter needs `iam:identities:create` plus `iam:bindings:create` on each granted role and `iam:groups:update` on each group, so invitations cannot grant more than the inviter could bind directly. Tenant aliases are public discovery data by design (`tenants.lookup` needs no credential, like an AWS account alias); apply ingress rate limits to it and do not encode secrets in aliases. Managed resource registrations are trusted authorization inputs: `iam:resources:*` permissions decide who may register or edit them, and attribute values are validated against the declared schema.

Access requests grant nothing by themselves: approval creates bindings under the reviewer's grant authority and re-checks `iam:bindings:create` on every role, so the review permission can never widen what the reviewer could bind directly, and a requester cannot review their own request. Temporary bindings stop granting the moment they expire, before the purge worker removes them. Webhook subscriptions are tenant-scoped; only root may subscribe to a subtree, secrets are sealed at rest and shown once, deliveries carry audit metadata only, and endpoints must verify the HMAC signature and timestamp before trusting a delivery.

Delegated administrators cannot remove their own parent-controlled ceilings, borrow a superior authority, or edit protected owner definitions. Moving a tenant requires recent authentication plus authority in the destination parent; the hierarchy's type, depth, and cycle rules apply, and delegation chains keep their original grant authorities. Retention purges are deployment operations: they remove tombstoned tenants after an explicit retention window, invoke plugin purge callbacks in the same transaction, and preserve audit records. Tenant-created actions cannot redefine platform namespaces. Account linking supplies no cross-tenant permission.

## Authentication

Passwords use Argon2id and must be at least 12 characters. By default a small built-in screen also refuses well-known passwords, keyboard walks, sequences, and passwords with fewer than five distinct characters (`authentication.passwordPolicy.blockCommonPasswords: false` turns it off). `passwordPolicy.isBreached` adds a breach corpus — `pwnedPasswords()` from `@better-iam/auth` is a Have I Been Pwned client that sends only a five-character SHA-1 prefix (k-anonymity), times out after three seconds, and fails open unless `failClosed` — and `passwordPolicy.check` adds a custom rule. Tenants tighten further through their authentication policy: `minPasswordLength`, `passwordMinClasses` (2–4 character classes), `passwordRejectPersonalInfo` (no email local part or name word of four or more characters), `passwordHistory` (refuse the last 1–24 passwords, compared with Argon2 against the newest 24 retained hashes, which are deleted with the identity), and `passwordMaxAgeDays`. Every rule applies wherever a password is set: creation, invitations, bulk onboarding, reset, and change. An expired password is refused with `PASSWORD_EXPIRED` only after it has been verified, so expiry never reveals whether a guess was right; the person recovers through password reset. Secrets/challenges are generated with cryptographic randomness. Sessions and API keys store token hashes; short authentication codes use keyed digests. MFA seeds and delivery payloads use authenticated encryption. Recovery codes are hashed and single-use. Passkeys verify challenge, origin, RP ID, user verification, and cryptographic signatures.

Sessions have absolute and idle expiry, are revoked on sensitive credential changes, and can be ended individually or all-but-current by their owner. Client details recorded on sessions (user agent, proxy-derived IP, device label) are informational: nothing about the client is trusted for authorization, and an IP is recorded only when `http.clientInfo` derives it from a proxy header you control. Login attempts, MFA, and recovery use shared persisted rate limits per account, and `rateLimits.ipAttempts` adds one per client IP across every flow of a tenant so that spraying many accounts from one address is bounded like hammering one (it needs a recorded IP and is sized by the operator for offices behind one NAT). Root and configured tenant MFA requirements also apply to federation and recovery; resetting a password does not remove MFA.

A tenant's authentication policy (`tenants.setAuthPolicy`, under `iam:tenants:update` with recent authentication) can only tighten the deployment's configuration: require MFA for every person in the tenant, restrict the accepted sign-in methods, and shorten session lifetimes. Method restrictions are checked before any credential is examined so a rejected method never reveals whether a password was right. Existing sessions are re-validated against the policy on their next use, so requiring MFA locks out non-MFA sessions immediately, and a person cannot disable MFA while the tenant requires it. `requireMfaForOwners` applies the same requirement to owners only, so the people who can change the policy are protected first. Each user session records the method that established it (`session.method`), available to policies as `principal.authMethod`.

"Remember this device" (`verifyMfa` / `confirmMfa` with `rememberDevice`) issues an opaque device token, stored hashed, that lets the same browser satisfy the MFA requirement on later password or passwordless sign-ins for at most `authentication.trustedDeviceLifetimeMs` (30 days by default, one year at most; 0 disables) and a tenant's `trustedDeviceDays`, whichever is shorter. Root administrators are never remembered, an invalid or expired token simply leads to the normal challenge, and every remembered device is forgotten when the person changes their password, email, or factors, when an administrator revokes their sessions, and on `revokeTrustedDevices`. Sessions established this way carry `trustedDeviceId`, people see and forget their devices (`listTrustedDevices`, `revokeTrustedDevice`), and the HTTP layer keeps the token in its own `better-iam.device` cookie (HttpOnly, `__Host-` over HTTPS) that it injects into `signIn` and `finishPasswordless` bodies.

Emailed one-time codes (`mfaEmailCodes` on the tenant policy, or `authentication.mfaEmailCodes` for the deployment; off by default) let a tenant require MFA without forcing every member to install an authenticator: when nothing is enrolled, the sign-in response carries `emailCodeAvailable`, `auth.requestMfaCode` emails a six-digit code bound to that login challenge (hashed at rest, single use, ten minutes at most, sensitive rate limit), and `verifyMfa` accepts it. A code is weaker than an authenticator because it rides on the mailbox, so people with an authenticator enrolled, and root administrators always, must use the authenticator or a recovery code; the address must be verified.

A registered passkey can also serve as the second factor (`beginPasskeyMfa` / `finishPasskeyMfa`): the assertion is verified like a passkey sign-in (challenge, origin, RP ID, user verification, signature, counter) and is bound to the pending login challenge, which must still be open and belong to the same person; both challenges are consumed together.

A tenant can restrict where its people sign in from: `allowedIpRanges` (IPv4/IPv6 addresses or CIDR blocks) refuses session issuance, including impersonation, with `IP_NOT_ALLOWED` when the recorded client IP lies outside every range, and a session whose recorded IP falls outside the ranges stops working at its next use, so tightening the list cuts off existing sessions. The check needs an IP: configure `http.clientInfo` behind a proxy you control, because a sign-in without a recorded IP (direct API use, or the handler without `clientInfo`) is not judged. Refusals show up as `denied` spans with code `IP_NOT_ALLOWED`.

People can read their own authentication trail without any administrative permission (`auth.listSecurityEvents`: the `auth:*` audit events recorded for their identity, with the administrator named when one acted through impersonation). With `authentication.signInNotifications` (or a tenant's `notifyNewSignIn`), a session that starts from a client no live session or remembered device of theirs has used queues a `new-sign-in` email carrying the session ID, method, user agent, IP, and label, so a stolen password is noticed quickly; sessions without client details are never judged.

Failed attempts against a real, active account (a wrong password, authenticator or emailed code, or recovery code once the first factor passed) are recorded as `auth:signin:fail` events with the reason and the client's IP and user agent, in a transaction of their own after the refused flow rolled back, and counted in the person's sign-in record. Each new session carries that record (`session.previousSignIn`: previous sign-in time and client, failures since, and the latest failed attempt's time and client), so people learn about guessing against their account the next time they sign in even when no notification email reaches them. Attempts the rate limiter refused, unknown addresses, and disabled accounts produce no record and no event, so the mechanism neither enumerates accounts nor lets an attacker grow the audit log beyond the rate limit. `authentication.failedSignInAlerts` turns the count into one `sign-in-failures` email per streak (sent to verified addresses only, exactly when the streak reaches the threshold), so the person hears about it without waiting for their next sign-in and an attacker cannot use repeated attempts to flood their mailbox.

Network blocks are the incident-response counterpart of the allowlist. `security.blockNetwork({ tenantId, network, reason, durationMs?, platform? })` (`iam:security:manage`, recent authentication, audited as `security:network-block`) refuses every authentication flow and every live session whose recorded client IP falls in the network (an IPv4/IPv6 address or CIDR block) with `IP_BLOCKED`, before rate limits or credentials are examined, so a blocked address cannot count against anyone; root administrators set `platform` blocks on the root tenant that apply to every tenant, an organization's blocks apply to itself. A block lapses after `durationMs` (one minute to a year) or stays until `security.unblockNetwork` lifts it; `security.listBlocks` (`iam:security:read`) shows them with `active`. The caller's own recorded address is refused so nobody locks themselves out, and the authentication service reuses each tenant's list for five seconds, so a change reaches other processes within that time. Like the allowlist, blocks need `http.clientInfo` to record addresses. A tenant that wants stolen cookies to be useless elsewhere sets `bindSessionsToIp`: a user session is then accepted only from the address it was issued from, a use from another address is refused with `SESSION_NETWORK_MISMATCH` and recorded in the person's trail as `auth:session:mismatch` (both addresses in the metadata), and the person simply signs in again from the new network while the old session keeps working from the old one; sessions and requests without a recorded address are not judged. The admin panel's Sign-in failures page blocks a source address platform-wide for a day in one click and lists the platform's blocks; organization owners manage theirs on the settings page.

Impersonation ("view as", `identities.impersonate`) is off until a tenant's authentication policy sets `allowImpersonation`. It then needs `iam:identities:impersonate` on the member, recent authentication, an ordinary session of the administrator's own, and a recorded reason. Owners, root administrators, service accounts, and the caller cannot be impersonated. The member session inherits the administrator's MFA state (a member who requires MFA cannot be impersonated without it), lasts at most eight hours and never longer than the administrator's session, ends the moment the administrator signs out or is disabled, and appears in the member's own session list. It cannot perform anything that requires recent authentication (password, email, factor, session, and ownership changes), cannot re-authenticate, assume roles, grant OAuth consent, or impersonate further. Every audit record it produces carries `impersonatorId` beside the member `actorId`, policies see `principal.impersonated` and `principal.impersonatorId`, assertions carry `impersonatorId`, and the token is never issued as a cookie.

Stateless assertions (`assertions.issue`) are short-lived HS256 JSON Web Tokens describing the caller (identity, tenant, session kind, MFA, method, role and group IDs, optional public claims) for a named audience. Issuing one is authorized as `iam:assertions:create` on `iam/{audience}` and audited, so administrators decide which roles may obtain tokens for which services. They are signed with a key derived from the deployment secret (`iam.assertionKey()`); a service holding only that key verifies with `verifyAssertion` and cannot recover the secret. Assertions grant nothing inside IAM, cannot be exchanged for sessions, and are not revocable before they expire (at most one hour, five minutes by default), so keep lifetimes short and treat the derived key as a shared secret between IAM and its services.

Audit records form a per-tenant hash chain (`sequence`, `previousHash`, `hash`) that `audit.verify`, `audit.export`, and the portable `verifyAuditChain` check; see [events](events.md). The chain detects alteration, reordering, or removal by anyone who cannot rewrite both the events and the chain head. Export chains to independent storage and treat the exported heads as the reference.

HTTPS cookies use `__Host-better-iam.session`, Secure, HttpOnly, SameSite=Lax (or Strict with `http.cookieSameSite`), and Path=/. They carry a `Max-Age` equal to the session's remaining lifetime unless the request that issued the session asked for a browser-session cookie (`X-Better-IAM-Persistent: 0`, or `http.persistentCookies: false` as the default), in which case the browser drops the cookie when it closes while the server session still expires on its own schedule. Loopback HTTP development uses a separate non-prefixed cookie name. JSON mutations require `X-Better-IAM: 1`; cookie requests also require an exact trusted Origin. No parent-domain cookie is configured.

Sign-in results never carry token material other than the token itself: every flow that issues a session (`signIn`, `verifyMfa`, `confirmMfa`, `recoverMfa`, `finishPasswordless`, passkeys, `reauthenticate`, invitations, `links.switch`) returns `{ token, session }` where `session` is the public projection without `tokenHash` or `uniqueKey`, for in-process callers (server actions) as well as HTTP, and the HTTP handler additionally strips both fields from any top-level `session` object in a JSON response. The `Authorization` scheme is matched case-insensitively (`bearer` works). `credentials.revoke` deletes only API keys (`INVALID_CREDENTIAL` for any other session id), so it cannot end a person's session by id.

## Temporary credentials

Role sessions, session tokens and web-identity sessions are described in [temporary credentials](temporary-credentials.md). The properties they keep:

- **Typed, checksummed tokens.** Opaque credentials are `biam_<ses|key|rol|sts>_` plus 43 random base64url characters and a 6-character CRC-32 checksum (58 characters). A prefixed value with a bad shape or checksum is refused before any storage read; the stored session kind must match the prefix, and the prefix is never trusted for authorization. The checksum is public and authenticates nothing; it exists so secret scanners and log redaction can match `credentialTokenScanPattern` (`(?<![A-Za-z0-9_-])biam_(?:ses|key|rol|sts)_[A-Za-z0-9_-]{49}(?![A-Za-z0-9_-])`) with few false positives. Legacy unprefixed tokens keep working until they expire. Only SHA-256 hashes are stored.
- **Bounded by the source.** A temporary credential expires no later than its source, is re-validated recursively against it on every use, and never refreshes the source's idle timer. A session token also keeps the source's policy (an API key's scopes, as `sourcePolicy`) and credential authority as boundaries. A role session does not: it acts with the role's permissions, bounded by the trust's `ceiling`, its own optional session `policy`, the target tenant's boundaries and the role's authority, and the source's scopes or policy bound only the `iam:roles:assume` decision, which is re-evaluated on every use. A narrowly scoped API key or session token can therefore yield a role session that does more than the key itself; narrow the role, the trust `ceiling` or the session `policy` instead. Role sessions cannot chain (`ROLE_CHAINING_DISABLED`) and session tokens cannot mint session tokens (`CREDENTIAL_CHAINING_DISABLED`), so validation depth is at most two.
- **Never recent, owner, root or self-service.** `auth.requireRecent` refuses every session that is not a `user` or `api-key` session, or that has a source session, with `RECENT_AUTH_REQUIRED` ("Temporary credentials cannot perform this operation; use a signed-in session"). Before this, a role session inherited its source's sign-in time and passed for five minutes. Temporary credentials are never tenant owners or root administrators (no root override) and are refused by self-service actions. Impersonation keeps `IMPERSONATION_RESTRICTED`.
- **Caller-chosen attributes are closed by default.** Session tags and source identities can satisfy ABAC conditions, so an identity trust admits none until root sets `allowedTagKeys` or `sourceIdentityMode`. New cross-tenant trusts do not pass the source identity's attributes (`passSourceAttributes: false`), so another tenant's attribute values cannot satisfy this tenant's conditions; `analysis.findings` reports older trusts that still pass them (`trust-passes-foreign-attributes`).
- **Server-owned context keys.** Every `principal.*` key the server derives, `request.time`, `request.sourceIp`, and the whole `principal.sessionTags.` family are removed from `resolveContext` and plugin context before the server assigns its own values, so an application or plugin can no longer supply (or spoof) `principal.authMethod`, `principal.impersonatorId`, a session name, tags, or a source address, even when the server leaves the key absent. The new session names (`sessionId`, `tokenIssueTime`, `authTime`, `mfaTime`, `sourceTenantId`, `sessionName`, `sourceIdentity`, `sessionTags`, `sessionTagKeys`, `webIdentityProvider`, `webIdentitySubject`) are reserved and cannot be declared as identity attributes (`INVALID_CONFIG`). `request.sourceIp` is set only from the client address the server recorded (`http.clientInfo` or `auth.withClient`), never for simulations.
- **Session JWTs are hybrid.** With `sts.jwt`, role sessions and session tokens can be issued as JWTs (`typ: biam-session+jwt`, EdDSA or ES256 only, algorithm pinned per `kid`, `jku`/`x5u`/embedded keys ignored, at most 4096 characters). IAM accepts one only when the signature, type, issuer, times and lifetime verify, its audience contains the IAM issuer, and a stored session row with the same id, kind, identity, tenant and token hash exists, so every revocation inside IAM is immediate and a validly signed token (after a key leak, say) still cannot name an arbitrary session. Offline verifiers in other services learn of revocation only at `exp` (at most `sts.jwt.maxLifetimeSeconds`, one hour by default): use 5 to 15 minute tokens for high-risk services, or check online with `sts.getCallerIdentity` or `iam.sessionTokens.verify`. Removing a `kid` from both key lists is the emergency revoke. Audiences other than the issuer need `iam:assertions:create` on `iam/{aud}`, and a token scoped to a downstream audience is refused by IAM. JWTs never carry tags, policies, authority ids or hashes, and are never cookies (user sessions and API keys are never JWTs).
- **Signing keys are separate.** `sts.jwt` keys are configured on their own, never derived from `options.secret` (so `rotate-secrets` does not affect them) and never shared with the OAuth provider, whose `at+jwt` access tokens have their own keys and `typ`. `verificationKeys` must be public-only.
- **Web identity.** The exchange is public, so it is rate limited per trust (`sts.webIdentity.maxExchangesPerWindow`) before any lookup, and every refusal that depends on stored state or the token is the same `WEB_IDENTITY_REJECTED` body; trust ids are random UUIDs. Because each attempt with a new trust id writes a limiter row, also set `authentication.rateLimits.ipAttempts` (with `http.clientInfo`) and ingress limits. Provider keys are fetched with an SSRF guard: https on port 443 only, a resolver that refuses loopback, private, CGNAT, link-local, unique-local, multicast, reserved, documentation, NAT64/6to4/Teredo and IPv4-mapped private addresses (IP-literal hosts too), no redirects, a timeout, a size cap and a JSON content type; `allowPrivateNetworks` and `allowInsecureLocalhost` are for development only, and `fetchJson` hands the transport (and its safety) to the host. At most 32 fetched keys are used, RSA keys need 2048 bits, keys are cached per provider with a 30-second negative cache and a 30-second refetch cooldown for unknown `kid`s, and nothing is fetched at registration. Tokens with `typ` `biam-session+jwt` or `at+jwt`, symmetric algorithms and `none` are refused, and IAM's own issuer cannot be registered. Trust conditions must pin `token.sub` (`WEAK_TRUST_CONDITIONS`). Single-use replay protection is store-backed and atomic with issuance. The raw external token is never stored or logged; audits record issuer and subject only after the signature verified. Sessions are bounded by the authority of both the trust's and the provider's creators, and the feature is off by default. Sessions admitted under old verification rules do not outlive them: an `oidcProviders.update` that changes keys, algorithms, audiences, token lifetime or clock tolerance, or disables the provider, moves the provider's watermark and deletes its sessions for good.

## External identity

OAuth uses state, PKCE, browser-bound callbacks, issuer/subject mappings, and OIDC nonce validation. SAML uses a maintained verifier plus exact destination/recipient/in-response-to checks and a shared replay cache. SCIM connection credentials are tenant-scoped, cannot provision root privileges, and protect owner accounts.

An email collision is not proof of account ownership. Explicit linking must prove control of the existing account and the external provider identity. Configure issuers, endpoints, certificates, signing keys, and redirect URLs only through trusted deployment configuration or authorized administration.

## Operational responsibilities

- Keep application and protocol keys stable, secret, backed up, and separate by purpose. Losing encryption keys makes enrolled factors and queued deliveries unreadable. Rotate the deployment `secret` with `previousSecrets` and `rotate-secrets` (see [deployment](deployment.md#rotating-the-deployment-secret)); never replace it outright.
- Require delivery transports to deduplicate IDs and avoid logging tokens or message payloads.
- Keep administrative policy explanations and audit records tenant-scoped.
- Preserve the adapter transaction contract. External side effects belong in an outbox or after commit.
- Use request/body limits and network rate limits at the ingress, in addition to account-level controls.
- Audit application resource loaders and custom plugins as trusted server code.
- Prefer eligible (just-in-time) bindings over standing privileged roles, require a justification and MFA for activation, and alert on `binding:*` events. Give contractors and temporary service accounts an `expiresAt`, and schedule `purgeDeleted` so expired identities are disabled promptly.
- Label API keys, review `credentials.list({ unusedForMs })` regularly, and revoke or rotate keys nobody uses; rotation keeps the label and resets the usage history.
- Keep tenant configuration in version control and roll it out with `config-plan` / `config-apply`; treat the applying token as an administrator credential, because every change it makes is authorized against that identity.
- Add `credentialTokenScanPattern` to your secret scanning and log redaction. Keep `sts.jwt` private keys in the secret store, rotate them with the runbook in [temporary credentials](temporary-credentials.md#session-jwts), and keep JWT lifetimes short for services that verify offline.
- Leave `sts.webIdentity` off until a workload needs it, pin `allowedIssuers` to the platforms you approve, give each workload its own service account, and pin every web trust to one subject.

Tests exercise adversarial cases but are not an independent penetration test or a security certification. Report vulnerabilities privately to the repository owner; do not include live secrets in reports.
