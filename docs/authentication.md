# Authentication guide

How people and services prove who they are, what a session carries, and which knobs a deployment and each organization have. The [security model](security.md) explains the guarantees; this guide explains the flows.

## Sign-in methods

| Method                       | Calls                                                                                      | Notes                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Password                     | `auth.signIn({ tenantId, email, password })`                                               | Argon2id; tenant password rules apply on creation, reset, and change.                                                                                                                                                                                                                                                                                                       |
| Magic link / emailed code    | `auth.startPasswordless` then `auth.finishPasswordless`                                    | `passwordlessEmail` / `passwordlessSms` must be enabled with `sendEmail` / `sendSms`. Never links accounts by matching an address.                                                                                                                                                                                                                                          |
| Passkey                      | `auth.beginPasskeyAuthentication` then `auth.finishPasskeyAuthentication`                  | Without an `email`, the options name no credential and the authenticator's discoverable passkey picks the account (browser autofill). Registered from a recently authenticated session (`beginPasskeyRegistration`, `finishPasskeyRegistration({ name? })`); `listPasskeys` reports name, `createdAt`, `lastUsedAt`, device type, and sync state, `renamePasskey` relabels. |
| Federated (OAuth/OIDC, SAML) | The protocol packages complete the ceremony and call `protocolHost.completeAuthentication` | See [protocols](protocols.md); `mapAttributes` stores provider attributes on the identity.                                                                                                                                                                                                                                                                                  |
| API key (service accounts)   | `Authorization: Bearer <key>`                                                              | Issued with `credentials.create`; expiring, rotatable, labeled, with `lastUsedAt`.                                                                                                                                                                                                                                                                                          |
| Assumed role                 | `roles.assume({ tenantId, trustId })`                                                      | Platform-controlled trust; sessions are short and cannot chain.                                                                                                                                                                                                                                                                                                             |
| Impersonation ("view as")    | `identities.impersonate`                                                                   | An administrator's session as a member; opt-in per tenant, restricted, fully attributed. See below.                                                                                                                                                                                                                                                                         |
| Session token                | `sts.getSessionToken({ durationSeconds?, policy?, sessionName?, mfaCode?, format? })`      | A short-lived `biam_sts_` token for your own identity from a user session or API key; optional TOTP step-up. See [temporary credentials](temporary-credentials.md#session-tokens).                                                                                                                                                                                          |
| Web identity                 | `sts.assumeRoleWithWebIdentity({ tenantId, trustId, webIdentityToken, sessionName })`      | Public exchange of a CI or workload OIDC token for a role session acting as a service account. See [temporary credentials](temporary-credentials.md#web-identity-federation).                                                                                                                                                                                               |
| Session JWT                  | `format: 'jwt'` on `roles.assume` and the two `sts` issuers                                | A signed, offline-verifiable form of a role session or session token (needs `sts.jwt`); IAM still checks the stored session on every use.                                                                                                                                                                                                                                   |

Every sign-in returns either `{ token, session }` or `{ mfaRequired: true, challenge, enrollmentRequired, emailCodeAvailable? }`. The session's `method` (`password`, `passwordless-email`, `passwordless-sms`, `passkey`, `federated`, `impersonation`) reaches policies as `principal.authMethod`.

## Multi-factor authentication

MFA is required for root administrators, for anyone with an authenticator enrolled, when the tenant policy sets `requireMfa`, and when the deployment's `authentication.requireMfa(tenant, identity)` callback says so. When a sign-in returns `mfaRequired`:

1. **Authenticator enrolled** (`enrollmentRequired: false`): `auth.verifyMfa({ tenantId, challenge, code })` with a TOTP code, or `auth.recoverMfa` with a recovery code. Each TOTP time step is accepted once.
2. **Nothing enrolled** (`enrollmentRequired: true`): `auth.beginMfa({ tenantId, challenge })` returns a secret and `otpauth://` URI; `auth.confirmMfa({ credential: { tenantId, challenge }, code })` enables the factor, returns ten single-use recovery codes, and issues the session.
3. **Emailed code** (`emailCodeAvailable: true`; tenant policy `mfaEmailCodes` or deployment `authentication.mfaEmailCodes`): `auth.requestMfaCode({ tenantId, challenge })` emails a six-digit code bound to that challenge; `auth.verifyMfa` accepts it once. Only for people with nothing enrolled and a verified address; never for root administrators.
4. **Passkey** (`passkeyAvailable: true`, whenever the person has a passkey registered): `auth.beginPasskeyMfa({ tenantId, challenge })` returns WebAuthn request options bound to that challenge; the browser runs `startAuthentication` (`better-iam/client/passkeys`) and `auth.finishPasskeyMfa({ tenantId, challengeId, response, rememberDevice? })` verifies the user-verified assertion and issues the session. Both the passkey challenge and the login challenge are consumed.

`rememberDevice: true` on `verifyMfa` / `confirmMfa` returns a `deviceToken` (and `deviceExpiresAt`) when the deployment (`trustedDeviceLifetimeMs`, 30 days by default) and the tenant (`trustedDeviceDays`) allow it. Passing that token to `signIn` / `finishPasswordless` later satisfies the MFA requirement; through the HTTP handler it travels in the `better-iam.device` cookie automatically. People list and forget their devices (`listTrustedDevices`, `revokeTrustedDevice`, `revokeTrustedDevices`); any password, email, or factor change forgets them all. Root administrators are never remembered.

From a signed-in session, `auth.beginMfa` / `confirmMfa` enroll, `regenerateRecoveryCodes` replaces the codes, and `disableMfa` removes the factor unless the tenant or the root role requires it. All three need recent authentication.

## Sessions

A user session has an absolute lifetime and an idle timeout (deployment `sessionLifetimeMs` / `sessionIdleTimeoutMs`, shortened per tenant), records the sign-in method and client details (`client.userAgent`, `client.ip`, `client.label`, captured by `http.clientInfo` or `auth.withClient`), and is revalidated on every use: identity and tenant status, MFA requirement, impersonation source, tenant network allowlist. `auth.getSession` returns the identity, the session, and `limits` (the tenant's `lifetimeMs` and `idleTimeoutMs`, and `idleExpiresAt`, when the session lapses if nothing touches it again, which the call itself just did), so a client can warn before an idle sign-out and keep the session alive on request (the console does: a countdown two minutes ahead with "Stay signed in", and a return to the login page once the session has lapsed); `auth.listSessions` lists the caller's own (with `current` on the calling one); `auth.mfaStatus` summarizes what a person has set up (authenticator, unused recovery codes, passkeys, remembered devices, whether this session passed MFA); `auth.revokeSession`, `auth.revokeOtherSessions`, and `auth.signOut` end them. Administrators end someone else's with `identities.revokeSessions`, or everyone's with `tenants.revokeSessions`. The tenant policy's `maxSessions` caps concurrent sessions per person (the oldest ends).

Sensitive operations (password, email, factor, device, session, ownership changes, impersonation, policy changes) require **recent authentication**: the session must have been established within `recentAuthenticationMs` (five minutes by default). `auth.reauthenticate({ password })` refreshes that without a new sign-in; the console prompts for it when an operation answers `RECENT_AUTH_REQUIRED`.

`auth.listSecurityEvents` gives people their own authentication trail (sign-ins, failed attempts, sign-outs, factor and password changes, remembered devices), naming the administrator when one acted through impersonation and carrying each event's `metadata` (the client's `ip` and `userAgent`, the sign-in `method`, or a failure's `reason`). With `authentication.signInNotifications` or a tenant's `notifyNewSignIn`, a session from a client none of the person's live sessions or remembered devices has used queues a `new-sign-in` email.

Every sign-in flow keeps a small sign-in record per person: when their last session was issued and from which client, and how many attempts since then named their account with a wrong password, authenticator or emailed code, or recovery code (`auth:signin:fail` audit events with `reason: 'password' | 'mfa' | 'recovery-code'`, recorded in a transaction of their own because the refused flow rolled back). A new session carries that record as `session.previousSignIn` (absent on a first sign-in) and the record restarts, so an application can greet people with "last sign-in on Tuesday from Chrome, 3 failed attempts since" the way a login banner does. Unknown addresses, disabled accounts, and attempts the rate limiter refused are never counted, so the record cannot be used to enumerate accounts or to flood the audit log. The console shows the notice above every page of the affected session and the record on the account page. With `authentication.failedSignInAlerts` set, the person also receives one `sign-in-failures` email the moment the streak reaches that number, so they hear about a guessing attempt before their next sign-in.

When an address keeps guessing, block it: `security.blockNetwork` refuses every sign-in flow and live session from a network (`IP_BLOCKED`, before rate limits and credentials) for one tenant, or platform-wide when a root administrator sets `platform` on the root tenant; `security.unblockNetwork` lifts it, `security.listBlocks` shows them, and a `durationMs` makes a block lapse by itself. See [security](security.md#authentication).

## Account recovery and changes

- Password reset: `auth.requestPasswordReset({ tenantId, email })` always succeeds (no account enumeration) and emails a `password-reset` token; `auth.resetPassword({ tenantId, token, password })` sets the password and ends every session. Administrators can trigger it for a member with `identities.requestPasswordReset`.
- Password change: `auth.changePassword({ currentPassword, password })` (recent authentication; other sessions end).
- Email: `auth.requestEmailVerification` / `auth.verifyEmail` for the current address; `auth.requestEmailChange` / `auth.confirmEmailChange` to move to a new one (recent authentication; the new address must be confirmed). Administrators change an address with `identities.update({ email })`.
- Phone: `auth.startPhoneVerification` / `auth.confirmPhoneVerification` enable SMS codes.
- Lockouts: sign-in, recovery, and MFA flows share persisted rate limits (`authentication.rateLimits`, tightened per tenant with `maxAttempts`); `identities.unlock` clears them for one person. A `RATE_LIMITED` error carries `retryAfterMs`, the HTTP response adds a `Retry-After` header, and `IamClientError.retryAfterMs` exposes it to browser code.

## Tenant authentication policy

`tenants.setAuthPolicy` (owner or `iam:tenants:update`, recent authentication) layers rules under the deployment's configuration and can only tighten it:

| Field                                                                                                            | Effect                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `requireMfa`                                                                                                     | Every person must complete MFA; those without a factor enroll on their next sign-in.                                                                                                                     |
| `requireMfaForOwners`                                                                                            | Only owners must complete MFA (the usual first step before requiring it for everyone).                                                                                                                   |
| `allowedMethods`                                                                                                 | Accepted sign-in methods; refused before any credential is examined.                                                                                                                                     |
| `sessionLifetimeMs`, `sessionIdleTimeoutMs`, `maxSessions`                                                       | Shorter sessions; a cap on concurrent sessions per person.                                                                                                                                               |
| `maxAttempts`                                                                                                    | Tighter rate limits for the tenant's authentication flows.                                                                                                                                               |
| `minPasswordLength`, `passwordMinClasses`, `passwordRejectPersonalInfo`, `passwordHistory`, `passwordMaxAgeDays` | Password rules on top of the deployment's screening.                                                                                                                                                     |
| `trustedDeviceDays`                                                                                              | How long "remember this device" may skip MFA; `0` turns it off.                                                                                                                                          |
| `mfaEmailCodes`                                                                                                  | Offer emailed one-time codes to people without an authenticator.                                                                                                                                         |
| `allowImpersonation`                                                                                             | Let administrators with `iam:identities:impersonate` open "view as" sessions.                                                                                                                            |
| `allowedIpRanges`                                                                                                | Networks sessions may be issued and used from (needs recorded client IPs).                                                                                                                               |
| `notifyNewSignIn`                                                                                                | Email people about sessions from unfamiliar clients.                                                                                                                                                     |
| `bindSessionsToIp`                                                                                               | A session works only from the IP it was issued from; elsewhere it is refused (`SESSION_NETWORK_MISMATCH`, recorded as `auth:session:mismatch`) and the person signs in again. Needs recorded client IPs. |

`tenantDefaults.authPolicy` on the server options applies a policy to every tenant created later.

## Temporary credentials

Role sessions, session tokens and web-identity sessions derive from a source credential and never outlive it; the full guide is [temporary credentials](temporary-credentials.md).

- **Assuming a role.** `roles.assume(credential, { tenantId, trustId, externalId?, durationSeconds?, policy?, sessionName?, sourceIdentity?, tags?, format?, audience? })` works from a user session (not impersonated), an API key, or a session token, and refuses role sessions (`ROLE_CHAINING_DISABLED`). `durationSeconds` is 60 up to the smaller of `sts.maxRoleSessionSeconds` (3600 by default) and the trust's `maxSessionSeconds`, 900 by default, and a value outside that range is `INVALID_INPUT`; the session never outlives its source. `sessionName` and `sourceIdentity` match `/^[\w+=,.@-]{2,64}$/`; `tags` (at most 50) and `sourceIdentity` are admitted only when the trust allows them. The response is `{ token, tokenType: 'Bearer', format, expiresAt, expiresIn, audience?, session: { id, tenantId, kind, identityId, expiresAt, mfa, roleId, trustId, sessionName?, sourceIdentity? } }`, a superset of the earlier `{ token, session }`.
- **Step-up for automation.** `sts.getSessionToken(credential, { mfaCode })` from a person's session verifies a current authenticator code (single use, sensitive rate limit, audited as `auth:mfa:step-up`) and returns a token with `mfa: true`; that token can then assume roles through trusts with `requireMfa`. API keys cannot pass a code (`MFA_NOT_ENROLLED`).
- **Who am I.** `sts.getCallerIdentity(credential)` works for every kind (user, impersonation, API key, role session, session token, JWT) and doubles as an online revocation check; `auth.getSession` stays user-only and answers `UNAUTHENTICATED` for other kinds. The CLI's `whoami` prints it.
- **Recent authentication.** Temporary credentials never pass `requireRecent`: operations that need it answer `RECENT_AUTH_REQUIRED` for role sessions and session tokens whatever their age. Sign in for those operations; an API key passes only within `recentAuthenticationMs` of its creation or rotation.
- **Transport.** Temporary tokens travel only as `Authorization: Bearer` (the scheme is case-insensitive) or `{ token }`; issuers return them once in the body and never set a cookie. Session JWTs contain dots, so they can never be cookies. `auth.listSessions` shows a person's own session tokens (without hashes) and `auth.revokeSession` ends one.

## Impersonation

When a tenant allows it, `identities.impersonate({ tenantId, identityId, reason, durationMs? })` returns a token for a session as the member: it inherits the administrator's MFA state, lasts at most eight hours and never beyond the administrator's own session, cannot do anything that needs recent authentication, assume roles, grant OAuth consent, or impersonate further, and ends when the administrator signs out or is disabled. Every audit record it produces carries `impersonatorId`, policies see `principal.impersonated`, and the member sees the session in their own list. The token is returned in the body only, never as a cookie.

## HTTP behaviour

Through `iam.handler`, every `auth/*` method is `POST {basePath}/auth/{method}` with a JSON body and the `X-Better-IAM: 1` header. Responses that issue a session set the `better-iam.session` cookie (`__Host-` prefixed over HTTPS, HttpOnly, SameSite=Lax); `auth/signOut` clears it; a `deviceToken` in a response also sets the `better-iam.device` cookie, which is injected into later `signIn` / `finishPasswordless` bodies and cleared by `auth/revokeTrustedDevices`. Cookie-bearing requests must carry an exact trusted `Origin`. Bearer tokens (`Authorization: Bearer …`) work for every method and never touch cookies. `GET {basePath}/health`, `GET {basePath}/metrics` and, when `sts.jwt` is configured, the public `GET {basePath}/.well-known/jwks.json` are the only GET endpoints. The session cookie normally lasts as long as the session (`Max-Age`); a request that issues a session may send `X-Better-IAM-Persistent: 0` to receive a browser-session cookie instead, which disappears when the browser closes while the server session keeps its own lifetime ("keep me signed in" unticked in the console; `http.persistentCookies: false` makes that the default and `1` opts back in). `http.cookieSameSite: 'strict'` narrows both cookies from `SameSite=Lax` to `Strict`.

## Deployment options

Under `authentication`: `sendEmail`, `sendSms`, `emailPassword`, `passwordlessEmail`, `passwordlessSms`, `signUpEnabled`, `requireEmailVerification`, `sessionLifetimeMs`, `sessionIdleTimeoutMs`, `recentAuthenticationMs`, `trustedDeviceLifetimeMs`, `signInNotifications`, `failedSignInAlerts`, `mfaEmailCodes`, `rateLimits` (`attempts`, `sensitiveAttempts`, `windowMs`, `ipAttempts`, `limiter`), `requireMfa`, `passkeys`, `passwordPolicy`, `maxDeliveryAttempts`, and `now` (for tests). Email templates the outbox produces: `verify-email`, `password-reset`, `email-change`, `magic-link`, `code`, `mfa-code`, `new-sign-in`, `sign-in-failures`, `owner-invitation`, `member-invitation`; each carries a `token` or `code` your delivery callback renders into a message. `renderDeliveryMessage(message, { appName, links })` from `better-iam/auth/templates` (a subpath without native dependencies, so it also suits email workers and edge runtimes) turns any of them into `{ subject, text, html }` (HTML-escaped) using the link builders you supply for your own pages (`links.account({ tenantId })` gives the `new-sign-in` and `sign-in-failures` notices a "Review your account" button when the message carries its `tenantId`), falling back to the raw token when a builder is missing, and returns `undefined` for templates it does not know so your callback can render those itself:

```ts
import { renderDeliveryMessage } from 'better-iam/auth/templates';

sendEmail: async (message) => {
  const rendered = renderDeliveryMessage(message, {
    appName: 'Acme Cloud',
    links: {
      invitation: ({ kind, tenantId, token }) => `${origin}/join?kind=${kind}&tenant=${tenantId}&token=${token}`,
      passwordReset: ({ tenantId, token }) => `${origin}/reset?tenant=${tenantId}&token=${token}`,
    },
  });
  if (rendered) await mailer.send({ to: message.to, ...rendered });
},
```
