# Policies and delegation

```ts
import { definePolicy } from 'better-iam';

const reader = definePolicy({
  version: 1,
  statements: [
    {
      sid: 'OwnedDocuments',
      effect: 'allow',
      actions: ['documents:read'],
      resources: ['document/*'],
      conditions: { Bool: { 'principal.mfa': true } },
    },
  ],
});
```

## Permission catalog

The catalog is the set of action names a policy may use. It contains the built-in `iam:*` actions, the product's actions, plugin actions, and (when enabled) tenant-defined actions. Registering an action grants nothing.

```ts
permissions: {
  mode: 'tenant-defined', // or 'catalog' (default) to allow only developer-defined names
  actions: ['reports:export'], // actions without a resource type
  resourceTypes: {
    document: { actions: ['documents:read', 'documents:write'], attributes: { classification: 'string' } },
    project: { managed: true, actions: ['projects:read', 'projects:manage'], attributes: { archived: 'boolean' } },
    task: { managed: true, parent: 'project', actions: ['tasks:read', 'tasks:write'] },
  },
}
```

Policy documents are validated against the catalog when they are stored: an exact action name that does not exist is rejected with `INVALID_ACTION`. Once `resourceTypes` is configured, an exact resource type in a resource pattern must also exist (`INVALID_RESOURCE_TYPE`). Wildcard patterns such as `documents:*` or `*/report` are stored as written. The same validation applies to inline role documents, tenant boundaries, principal boundaries, grant-authority ceilings, trust ceilings, and session policies.

## Resource types and resources

Resource patterns match `type/id` within an already-resolved tenant. `*` and `?` are anchored glob wildcards, not regular expressions. They cannot change the target tenant.

A resource type is either **application-owned** or **managed**:

- Application-owned types require `resolveResource`, which must load ownership and attributes from trusted storage. Never copy the request tenant ID into a fetched record to satisfy the resolver. Types that are not declared at all are still passed to `resolveResource`, so existing integrations keep working; declaring them adds validation and documents the attribute schema.
- Managed types (`managed: true`, and every tenant-defined type) are registered with IAM through `iam.api.resources.register/update/get/list/delete`. Authorization resolves the registration, so no application callback is involved. Attribute values are validated against the declared schema; `ownerId` must be an identity of the same tenant; `parent` types require a registered parent resource of the declared parent type. Registering a resource requires `iam:resources:create` on `iam/{type}/{id}`, so policies can scope who may register which resources.

With `mode: 'tenant-defined'`, a tenant administrator can register resource types of their own (`iam.api.resourceTypes.register`). Tenant types are always managed. Their names cannot collide with reserved names (`iam`, `role`, `oauth-client`, `scim`, `tenant`, `identity`, `session`), platform resource types, or the namespace of any platform action. Tenant-defined actions are namespaced under a tenant-defined type as `{type}:{verb}`; `iam.api.actions.register` and the `actions` list on `resourceTypes.register` create them. Deleting a type or action is refused while resources or policies still use it.

## Roles and permissions

A role grants the union of its attached policies and its optional inline document. `roles.create` accepts either a `document` or a `permissions` list; a permissions list becomes an inline allow statement over every resource of the tenant (`resources: ['*']`), which is the usual shape for application roles such as _Editor_ or _Approver_. Use a full document when access depends on conditions. Inline documents are bounded by the role's grant-authority ceilings exactly like attached policies.

`identities.listBindings` returns the effective role set of an identity, including bindings inherited through groups. `roles.listBindings` and `bindings.list` show who holds a role. These are administrative reads that require `iam:bindings:read`.

Roles form a hierarchy through `inherits` (`roles.create`/`roles.update({ inherits: [roleId, ...] })`, at most 20 direct parents, no cycles, no protected roles; an empty list clears it): a role grants the union of its own policies and document and, recursively, everything the roles it inherits grant. Inherited grants are evaluated under the inheriting role's own authority ceilings as well as the inherited role's, so a delegated administrator who makes their role inherit a broader one gets no more than their ceiling allows. A role that others inherit cannot be deleted (`RESOURCE_IN_USE`) until they stop inheriting it. Configuration sync carries `inherits` by name and applies it once every role of the document exists, so a parent and its child can be introduced together.

## Evaluation

1. Validate the credential, current identity, tenant, and requested action/resource.
2. Apply the protected universal root override only to authenticated root administrators.
3. For ordinary principals, require an active tenant ancestry and matching session tenant.
4. Collect identity/group role grants and intersect them with tenant, principal, issuer/grant-authority, and session ceilings.
5. An applicable explicit deny overrides an allow. Without an effective allow, deny access.

`iam.authorize` evaluates one request; `iam.authorizeMany` evaluates up to fifty checks for one tenant in a single transaction and is intended for rendering menus and lists. Both are advisory to clients: the server must call `iam.require` (or `authorize`) immediately before performing the protected operation.

Grant authorities are retained as references, including creator authority for policies/roles. A lower-authority editor cannot broaden a policy after a superior attaches it. Removing a principal's delegation authority disables dependent grants; removing the administrator's membership alone does not delete historical provisioned access.

Owner role definitions are protected. Ownership transfer uses its dedicated API and protects the last active owner. Group membership changes may grant or remove deny policies, so they also require authority over the group's bindings.

Boundaries constrain; they never grant access. Principal/tenant ceiling mutation is platform-controlled. Delegation can create a narrower child authority while retaining its parent chain. There is no arbitrary policy-containment solver.

## Policy variables

A resource pattern or a `StringEquals`/`StringLike` value may reference a trusted context key as `${key}`:

```ts
{ effect: 'allow', actions: ['documents:*'], resources: ['document/*'], conditions: { StringEquals: { 'resource.ownerId': '${principal.id}' } } }
{ effect: 'allow', actions: ['folders:read'], resources: ['folder/home-${principal.id}'] }
```

The value is substituted before matching and always matches literally: a value containing `*` or `?` cannot widen a pattern. A variable whose key is absent from the context never matches. Variables may not appear in action names or in the resource type segment (the part before the first `/`), and a malformed reference such as `${principal.id` is rejected when the document is stored. Any key from `resolveContext` can be referenced, so `${principal.department}` works once the application supplies it.

## Reverse queries and batches

`iam.listAccessible({ tenantId, action, type })` and `client.listAccessible` return the registered resources of one managed type that the caller may perform an action on, with `limit`/`offset` paging over the accessible set and a `total`. Grants and boundaries are loaded once and evaluated against every registration, so list pages no longer need to know resource IDs up front. Application-owned types are not enumerable this way; use `authorizeMany` with the IDs the product already has. Like `authorizeMany`, the result is advisory.

`resources.registerMany` registers up to 100 managed resources in one transaction. Every item is authorized as `iam:resources:create` on `iam/{type}/{id}` before anything is written; a denied item rejects the whole batch and records only its denial.

## Access reviews

Three administrator-only reads under `iam:policies:simulate` explain access without creating sessions or granting anything. Each evaluates the identity in a synthetic session (`assumeMfa: true` simulates an MFA session, otherwise conditions on `principal.mfa` see `false`), so results are advisory and never enforcement.

- `policies.simulate({ tenantId, identityId, action, resource })` returns the full decision for one check, including matched statements.
- `policies.whoCan({ tenantId, action, resource, kind?, assumeMfa?, limit?, offset? })` lists every active identity (people, or service accounts with `kind`) that could perform the action on the resource, with the decision reason, plus a `total`. Root administrators are not listed because their override applies everywhere. The resource is resolved once; grants are loaded per identity, so the call scales with the tenant's directory size and is meant for review screens, not per-request checks.
- `policies.effectiveActions({ tenantId, identityId, resource, actions?, assumeMfa? })` evaluates every catalog action (or the given list of at most 200) against one resource for one identity, loading the identity's grants once. It returns `allowed` (the sorted action names) and `results` with a reason per action.

`analysis.findings({ tenantId, dormantDays?, includeSuppressed? })` (`iam:analysis:read`) scans the tenant's configuration and returns `summary` counts and `findings` ordered by severity. High: policies or inline role documents that allow `*` / `iam:*` on `*` without conditions (`unrestricted-admin-policy`), and owners or holders of such roles without an authenticator or passkey while the tenant does not require MFA (`admin-without-mfa`). Medium: unconditional service-wide wildcards such as `documents:*` (`broad-action-wildcard`), service accounts with full administration (`service-account-admin`), people who hold bindings or ownership but have not signed in for `dormantDays` (default 90; `dormant-access`), API keys unused for `dormantDays` or never used (`stale-api-key`), and trusts that do not require MFA (`trust-without-mfa`). Low: policies attached to no role, roles bound to nobody or granting nothing, and groups that hold bindings but have no members. System owner policies and protected roles are not reported as misconfiguration. Finding IDs are deterministic, so `analysis.suppress({ tenantId, findingId, reason })` and `analysis.unsuppress` (`iam:analysis:update`) record accepted risks that stay hidden until unsuppressed (or listed with `includeSuppressed`). The scan reads the whole tenant and is meant for review screens and scheduled reports.

The scan also reports standing privileged access: a person with a direct, permanent binding (not eligible, no end) to a role that grants full administration (`standing-privileged-access`, medium), which just-in-time eligibility or an end date would narrow. It reports eligible bindings nobody has activated within `dormantDays` (`unused-eligible-binding`, low; only allowed activation and approval events count, so a member cannot hide it through `authorize`), people whose manager is missing, deleted, or disabled (`orphaned-manager`, low), reporting lines that loop (`manager-cycle`, medium), and stored policies or inline role documents with lint warnings (`policy-lint`, low).

For trusts, `trust-passes-foreign-attributes` (medium) reports live cross-tenant identity trusts that still pass the source identity's attributes into role sessions (`passSourceAttributes` not `false`, which includes trusts created before the option existed); fix it with `trust.update({ passSourceAttributes: false })` and pass data through session tags. Web-identity trusts are left out of `trust-without-mfa`, because their claim conditions pin the workload and external tokens never carry MFA.

`analysis.lintPolicy({ tenantId, document } | { tenantId, policyId })` (`iam:policies:read`) checks a candidate or stored document the way the server will evaluate it. It first validates it against the catalog (`valid: false` with the error, such as `INVALID_ACTION`, otherwise), then reports warnings by statement:

- `unrestricted-admin` and `service-wildcard` (info): unconditional `*`/`iam:*` on `*`, and service-wide action wildcards.
- `unknown-context-key`: a condition key the server never sets (for example `request.ip`) and the configuration does not declare. For `request.ip` the warning adds "or use request.sourceIp, which the server sets from the client address", and for `principal.tokenIssuedAt` it suggests `principal.tokenIssueTime`. A `principal.sessionTags.<key>` key is known (an optional string) when the tag key is valid and unknown otherwise; the session keys that can be missing (`principal.sessionName`, `principal.sourceIdentity`, `principal.mfaTime`, `request.sourceIp`, …) trigger `optional-key-deny` like other optional keys, and Numeric operators on the timestamp keys (`principal.tokenIssueTime`, `principal.authTime`, `principal.mfaTime`) are type mismatches.
- `optional-key-deny`: a deny conditioned on a key that can be missing (`principal.authMethod`, identity attributes, resource attributes, application keys), which silently never applies without an `Exists` guard.
- `negated-variable`: a negated string operator whose variable may not resolve, which then evaluates true.
- `ignorecase-variable`: `StringLikeIgnoreCase` with a variable whose key has capitals, which never resolves.
- `array-key-string-operator` and `array-variable`: `principal.groups`, `principal.roles`, and relation lists used where only `ArrayContains` works.
- `type-mismatch`: an operator that can never match the key's type.
- `always-true-condition`, `duplicate-statement`, `shadowed-allow` (an allow an unconditional deny covers), and `deny-only` (info where noted).

The shadowing check has a work budget, so adversarial documents stay fast; past it an info `shadowed-allow-skipped` says so. `lintPolicy` is also exported from `better-iam/server` for offline use.

Role mining reads who holds what and suggests simpler grants. `roleMining.suggest({ tenantId, minIdentities?, minRoles?, kinds?, limit? })` (`iam:analysis:read`) returns `summary` counts and `suggestions`, each with a deterministic `id`, the roles and people involved, and `savings` (grants saved):

- `redundant-binding`: direct bindings of a role the person also receives through a permanent group membership, from a standing binding under the same grant authority that is at least as broad (no window, no later start, no earlier end), so removing them changes nothing.
- `group-binding`: a role every permanent member of a group (at least `minIdentities`, default 3) holds through a plain direct binding (standing, permanent, not from a package). Binding it to the group replaces the direct bindings; new members then receive it and leavers lose it.
- `duplicate-roles`: roles whose inline, attached, and inherited statements are identical.
- `bundle`: role combinations of at least `minRoles` (default 2) roles held together by at least `minIdentities` people, found as closed itemsets over everyone's standing roles and skipped when an access package or an inheriting role already has exactly those roles. Grant them as one [access package](privileged-access.md) or an inheriting role.

`roleMining.apply({ tenantId, suggestionId })` (`iam:analysis:update`) carries out a `group-binding` or `redundant-binding` suggestion in one transaction after recomputing it (`NOT_FOUND` once it no longer holds). The group binding is created under the authority the direct bindings share, so the caller needs that authority (or root), `iam:bindings:create` on the role, and `iam:bindings:delete` on every removed binding; suggestions whose direct bindings come from different authorities are listed with `applicable: false`. Bundles and duplicate roles are left to `packages.create` and role edits.

`roleMining.outliers({ tenantId, peerBy?, threshold?, commonShare?, minPeers? })` (`iam:analysis:read`) compares each active person with their peers: people with the same manager (`peerBy: 'manager'`, the default) or the same value of a declared identity attribute (`'attribute:department'`). A role is unusual when fewer than `threshold` (0.25) of the peers hold it and missing when at least `commonShare` (0.8) hold it; peer groups with fewer than `minPeers` (3) others are skipped, and just-in-time bindings count as held. Use it to spot access that outlived a move and to find what a new joiner still lacks. CLI `better-iam mine-roles --tenant ID [--peer-by KEY]` prints both reports as the `BETTER_IAM_TOKEN` holder; the console has a Role mining page with Apply and Create package buttons.

### Access usage and right-sizing

With `accessUsage: true` (or `{ flushIntervalMs?, maxBuffered? }`) the server records which actions each identity actually used: every allowed `authorize` / `authorizeMany` check and every allowed provisioning operation counts, except root overrides and calls made while impersonating someone. Uses are counted in memory and written in batches (every minute by default, sooner when `maxBuffered` pairs are waiting) to the `accessUsage` collection, one record per identity and action with `firstUsedAt`, `lastUsedAt`, and `count`; `accessUsageTracking` remembers when each tenant's recording began. Call `iam.flushAccessUsage()` before shutting down so buffered uses are not lost.

- `roleMining.usage({ tenantId, identityId?, limit?, offset? })` (`iam:analysis:read`) lists the records, most recently used first.
- `roleMining.rightSize({ tenantId, unusedDays? })` (`iam:analysis:read`) compares every live binding with its holders' use in the last `unusedDays` (default 90). A role's actions are the known actions its allow statements (own, attached, inherited) match. Each `entries` item is a person whose use of a role is `unused` (none of its actions) or `partial`, with the used and unused actions and whether the role reaches them directly or through a group; `roles` lists, per role, the actions no holder used, the candidates for a narrower role. `complete` turns true once usage has been recorded for the whole window; before that, "unused" only means "not since tracking began".

Both read methods write buffered usage first, so results include the latest checks. The console's Role mining page shows a Least privilege card with a Remove button for unused direct bindings.

`roleMining.reviewRecommendations({ tenantId, campaignId, unusedDays? })` (`iam:analysis:read`) suggests a decision for every item of an [access-certification campaign](#access-reviews): `revoke` when the account is disabled, deleted, or expired, or when the person did not use the role within `unusedDays` (default 90), and `keep` when they did. The evidence (`basis`) is recorded usage once it covers the whole window (`usageComplete`), otherwise the person's last sign-in; group items and service accounts without usage data get `none`. Reviewers still decide; the console's campaign page shows the suggestion and its reason next to each open item.

### Change impact preview

`impact.preview({ tenantId, change, resources, actions?, assumeMfa? })` (`iam:policies:simulate`) answers "who gains or loses what if I make this change?" before you make it. `change` is exactly one of `{ role: { roleId, ...update } }` (what `roles.update` takes: `permissions`, `document`, `policyIds`, `inherits`), `{ policy: { policyId, document } }`, or `{ deleteRole: roleId }`. The server applies the change the way the real call would, with the same validation, the same permission (`iam:roles:update`, `iam:roles:delete`, or `iam:policies:update` on the item), and the same edit rights (a role others inherit cannot be deleted, a lower authority's role cannot be edited), inside a transaction it always rolls back. Every holder of the affected roles is evaluated before and after against each of the 1-10 `resources`. The affected roles are the changed role, or the roles attaching the policy, plus every role inheriting them; holders are active identities with a binding to them, directly or through a live group membership, up to 200. The result lists per holder and resource the `gained` and `lost` actions (every known action, or the given `actions`), with `gainedTotal`, `lostTotal`, and `truncated` when holders were capped. Conditions, authority ceilings, boundaries, access windows, and just-in-time eligibility all count, because the ordinary evaluator runs; `assumeMfa` evaluates holders as MFA-verified. The result's `invariants` lists the [access invariants](#access-invariants) the change would newly break (`broken`, with the new violations) or make pass (`fixed`). The console's Change impact page previews role permissions, policy documents, and role deletion.

### Access invariants

Invariants are guardrails that hold whatever roles and policies say: "contractors can never delete the payroll workspace", "the on-call group can always restart production". `invariants.create({ tenantId, name, subject, action, resource, expect, mode?, assumeMfa?, description? })` (`iam:invariants:manage`) stores one:

- `subject`: exactly one of `{ identityId }`, `{ groupId }` (its live members), `{ attribute: { name, value } }` (active identities whose declared attribute equals the value), or `{ everyone: true }`; at most 500 people are evaluated per invariant.
- `action` and `resource` (`{ type, id }`, which must resolve): what is checked. `expect: 'deny'` means nobody in the subject may be allowed; `expect: 'allow'` means everyone in it must be.
- `mode`: `monitor` (default) only reports; `enforce` also guards changes. `assumeMfa` (default true) evaluates people as MFA-verified, the most they can reach.

`invariants.run({ tenantId, invariantId? })` (`iam:invariants:read`) evaluates them against the current configuration with the ordinary evaluator and returns per invariant `passed`, the `violations` (person and decision reason), and an `error` when it can no longer be evaluated (its group or resource is gone). `list`, `update`, and `delete` complete the set; names are unique per tenant, and a tenant holds at most 100.

Enforced invariants are evaluated before and after every operation that can change access — role and policy edits and deletions, binding creation and deletion, just-in-time activation and approval, group membership changes, identity creation and attribute changes, package assignment and approval, configuration apply, access-request review, relationship and resource changes and deletions, boundary and authority changes, root grants, closing certification campaigns, publishing agreements, and `roleMining.apply`. Enforcement evaluates every subject, not only the first 500. When the operation newly breaks one — or leaves it impossible to evaluate, for example by deleting the group or resource it names — it is refused with `INVARIANT_VIOLATION` (409) and its transaction rolls back. Violations that already existed are reported but do not block unrelated work, so an invariant can be switched to `enforce` while it is still broken. Changes made outside the operation envelope — scheduled jobs (purge, package reconciliation, auto-closing campaigns), inbound SCIM provisioning, and members accepting agreements — are not guarded; the scheduled monitor below reports what they break. The console's Access invariants page lists invariants with their status, toggles enforcement, and creates new ones. In CI, run `better-iam check-invariants --tenant ID --fail-on-broken` (as `BETTER_IAM_TOKEN`) after `config-apply`; it prints the run and exits with `INVARIANTS_BROKEN` when any invariant is broken or cannot be evaluated.

To be told when a monitored invariant breaks, schedule `iam.checkInvariants({ tenantId? })` (CLI `better-iam monitor-invariants`), a deployment operation that evaluates every organization's invariants, stores the outcome on each (`lastCheck`: `at`, `passed`, violating identity IDs), and records `invariant:broken` (with the new violators) when an invariant starts failing or gains violators and `invariant:restored` when it passes again. Each change is reported once, so a webhook subscribed to `invariant:*` alerts without repeating itself.

### Terms of use

Agreements are versioned documents a tenant asks its members to accept: an acceptable-use policy, an NDA, data-handling rules. `agreements.create({ tenantId, name, content, url?, required?, reacceptAfterDays? })` (`iam:agreements:manage`) publishes one at version 1; `content` is up to 50 000 characters of text (line breaks allowed), `url` an optional http(s) link, `required` defaults to true, and `reacceptAfterDays` makes acceptance lapse (annual re-acceptance). `agreements.update` edits it; with `newVersion: true` the change becomes the next version and everyone must accept again, without it (a typo fix) existing acceptances stay valid. `agreements.delete` removes it with its acceptances; `list` and `status({ agreementId })` (`iam:agreements:read`) report who accepted the current version and which active people still owe it.

Members need no permission for their own side: `agreements.listMine({ tenantId })` returns every agreement with `accepted` and the text, and `agreements.accept({ tenantId, agreementId, version })` records acceptance of the version they were shown (`VERSION_CONFLICT` once it changed), audited as `agreement:accept`. Both need an ordinary session of the tenant; impersonating administrators cannot accept for someone, and service accounts accept nothing (nothing is pending for them).

Enforcement is a policy decision. Every evaluation for a person in their own tenant carries `principal.agreements` and `principal.pendingAgreements`, so a statement such as

```json
{
  "effect": "deny",
  "actions": ["documents:*"],
  "resources": ["*"],
  "conditions": { "NumericGreaterThan": { "principal.pendingAgreements": 0 } }
}
```

holds back document access until every required agreement is accepted, and `{ "ArrayContains": { "principal.agreements": ["Beta program"] } }` grants something only to people who accepted an optional one. The console shows members the required agreements they owe at the top of every page with an "I accept" button, and its Terms of use page publishes, edits, and tracks them.

Access certification campaigns turn reviews into a recorded decision. `certifications.create({ tenantId, name, roleIds?, subjectType?, reviewerIds?, dueAt?, undecided? })` (`iam:certifications:manage`) snapshots the live bindings of every non-protected role (or the listed roles and subject type, at most 5000). Reviewers call `certifications.decide({ tenantId, campaignId, decisions: [{ itemId, decision: 'keep' | 'revoke', note? }] })` under `iam:certifications:review`; when the campaign names `reviewerIds` only they may decide, and nobody decides on their own access, directly or through a group (`SELF_REVIEW`). `certifications.get` (`mine: true` hides the caller's own items) and `certifications.list` report progress under `iam:certifications:read`. `certifications.close` (manage, recent authentication) applies the campaign: revoked items — and undecided ones when `undecided: 'revoke'` — are removed under the closer's grant authority, each revocation is audited as `iam:bindings:delete`, and every item records `kept`, `revoked`, `already-removed`, or `revocation-failed` (a binding a higher authority granted, left for that administrator). Closed campaigns keep their record until `certifications.delete`. When email delivery is configured, each named reviewer receives a `certification-review` email (payload `campaignId`, `campaignName`, `items`, and `dueAt` when set) queued in the campaign's transaction.

`reviewerMode: 'manager'` assigns each person's items to their active manager (`Identity.managerId`, which SCIM can maintain); items without one, and group items, go to the named reviewers, or to anyone holding `iam:certifications:review` when none are named. Managers decide their items with `certifications.review({ tenantId, campaignId, decisions })`, which needs no certification permission, only an ordinary (not impersonated) session of the tenant and the assignment, and is audited as `certification:review`; `certifications.listMine({ tenantId })` returns the open campaigns with items assigned to the caller. Through `decide`, a manager-assigned item may be decided only by that manager or by a holder of `iam:certifications:manage`. Each reviewer is emailed once with their own item count. `certifications.remind({ tenantId, campaignId })` (manage) emails every reviewer who still has undecided items a `certification-reminder` and returns `{ reminded, pending }`. `autoClose: true` (with `dueAt`) lets the deployment job `iam.closeOverdueCertifications({ tenantId? })`, or CLI `close-certifications`, apply the campaign once it is due, each in its own transaction and under the creator's grant authority (revocations the creator could not make are reported as `revocation-failed`), audited as `certification:auto-close` by `deployment-operator`. The `certification-review` and `certification-reminder` emails are rendered by `renderDeliveryMessage` with a `links.certification({ tenantId, campaignId })` button.

## Separation of duties

`sod.create({ tenantId, name, roleIds, mode?, description? })` (`iam:sod:manage`) declares 2–20 roles that nobody may hold together — directly, through group membership, or as eligible just-in-time bindings. In `prevent` mode (the default) every operation that can grant a role — `bindings.create`, group membership, `identities.createMany`, access-request approval, access-package assignment and approved package requests, and `config.apply` — compares the tenant's conflicts before and after it runs and fails with `SOD_CONFLICT` (409), rolling the transaction back, when it would create a new one; member-invitation acceptance is checked the same way. Conflicts that already existed when the rule was added (reported as `existingViolations`) never block unrelated work. `detect` rules only report. `sod.violations` (`iam:sod:read`) lists everyone holding conflicting roles with names, the access analysis reports each as a high-severity `separation-of-duties` finding, and `sod.list`, `sod.update`, and `sod.delete` manage the rules. Owner roles cannot be part of a rule. SCIM role mappings are not blocked; their conflicts appear in the reports.

## Temporary bindings and access requests

`bindings.create` accepts `expiresAt` (epoch milliseconds, in the future, within ten years). An expired binding grants nothing, disappears from `identities.listBindings`, `roles.listBindings`, and `bindings.list` (pass `includeExpired: true` to see it), and is deleted by the purge worker. `bindings.update` extends, shortens, or clears (`expiresAt: null`) the expiry under the same rules as `bindings.delete`: the caller needs `iam:bindings:create` on the role and must own the binding's authority or be root.

`startsAt` future-dates a binding: it is listed with its start (`identities.listBindings`, `roles.listBindings`, the access report's `starting` section) but grants nothing until then, and `bindings.update` moves or clears (`null`) the start. Group memberships can be temporary too: `groups.addMember({ ..., expiresAt })` ends the membership, and with it every grant and activation it carried, at that time; `groups.updateMember` extends, shortens, or clears the expiry, `listMembers` and `identities.listGroups` report `membershipExpiresAt`, re-adding a lapsed member renews the membership, and the purge worker removes lapsed records (`expiredMemberships`).

A binding may also carry an access window (`bindings.create({ ..., window: { from: '09:00', to: '17:00', timeZone: 'Europe/Berlin', days: [1, 2, 3, 4, 5] } })`, `bindings.update({ window })`, `null` to clear): outside the window the binding grants nothing, exactly like an expired one, and it starts applying again when the window next opens. Times are `HH:MM` in the named IANA time zone; a window whose end is not after its start wraps past midnight and counts as the day it starts on; `days` are 0 (Sunday) to 6 and default to every day. `identities.listBindings` reports `inWindow` for such bindings, reviews (`whoCan`, `effectiveActions`) reflect the window at evaluation time, and configuration sync carries `window` on group bindings.

Access requests let members ask for roles instead of asking an administrator to bind them:

1. A member with `iam:access-requests:create` calls `accessRequests.create({ tenantId, roleIds, justification?, durationSeconds? })`. Protected roles cannot be requested, a member may hold at most twenty pending requests, and identical pending requests are rejected. Requests expire after `accessRequests.lifetimeMs` (default seven days).
2. A reviewer with `iam:access-requests:review` calls `approve` or `deny`. Approval creates (or refreshes) one binding per role under the reviewer's own grant authority and requires `iam:bindings:create` on each role, exactly like `bindings.create`, so a reviewer can never grant more than they could bind directly. A requester cannot approve their own request. `durationSeconds` on approval overrides the requested duration; the resulting bindings carry `expiresAt` and `accessRequestId`.
3. Requesters see their own requests with `listMine` and may `cancel` a pending one. `list` and `get` require `iam:access-requests:read`.

### Eligible bindings (just-in-time access)

A standing binding applies at all times. An eligible binding (`bindings.create({ ..., eligible: true, maxActivationMs?, requireJustification?, requireMfa? })`) records that its subject _may_ hold the role, and grants nothing until the subject activates it:

- `bindings.activate({ tenantId, bindingId, durationMs?, justification? })` needs `iam:bindings:activate` on the role (`iam/{roleId}`), so a tenant can scope which roles a person may activate, and is made from an ordinary session of the tenant (never an assumed role or an impersonation session). The binding must apply to the caller directly or through a group they belong to. `durationMs` defaults to and is capped by `maxActivationMs` (one hour by default, seven days at most). `requireJustification` makes the justification mandatory and `requireMfa` refuses password-only sessions with `MFA_REQUIRED`. One live activation per binding and identity; the record returned carries `active`, `activatedAt`, and `expiresAt`.
- While the activation is live the role behaves like a standing binding: `principal.roles`, reviews (`whoCan`, `effectiveActions`), `identities.listBindings` (with `activation`), and every decision see it. When it expires, or the holder calls `bindings.deactivate`, or an administrator holding the binding's authority calls `bindings.revokeActivation`, the role stops applying at the next request. Leaving the group, deleting the binding, deleting the role, or turning eligibility off (`bindings.update({ eligible: false })`) ends activations too, and the purge worker removes expired ones.
- `bindings.listMine` lists the caller's own bindings (standing and eligible, with the live activation) under `iam:bindings:activate` on the tenant, so members can see what they may elevate to without `iam:bindings:read`. `bindings.list({ eligible })` and `bindings.listActivations({ bindingId?, identityId?, roleId?, includeExpired? })` serve administrators.
- `tenants.setAccessPolicy({ tenantId, accessPolicy })` (`iam:tenants:update`, recent authentication) sets floors for the whole tenant: `maxActivationMs` caps every binding's own maximum, `requireJustification`, `requireMfa`, and `requireApproval` apply to every eligible binding, and `approvalLifetimeMs` (one day by default) is how long a request waits. A binding may be stricter than the policy, never looser; `null` clears the policy. Audited as `tenant:access-policy`.
- With `requireApproval`, `bindings.activate` records a request instead (`status: 'pending'`, lapsing after 24 hours) and emails the members of `approverGroupId` (`activation-request`, when the deployment sends email). An approver calls `bindings.approveActivation({ activationId, durationMs?, note? })` or `bindings.denyActivation({ activationId, note? })` under `iam:bindings:approve` on the role; when an approver group is set only its members (or root) may decide, `managerApproval` lets the requester's manager (`Identity.managerId`) decide as well and emails them each request, and nobody decides on their own request. Approval makes the role live from that moment for the requested duration (or a shorter one the approver chooses), the requester is emailed the decision (`activation-decided`), and `bindings.listApprovals` shows a person the requests they may decide on; `bindings.listMine` reports `pendingActivation`, and `listActivations({ status: 'pending' | 'denied' })` lists requests and refusals. A requester cancels with `bindings.deactivate`.
- Every activation is audited: the operation as `iam:bindings:activate`, plus `binding:activate` with `activationId`, `roleId`, `expiresAt`, and the justification, and `binding:deactivate` (with `revoked: true` when an administrator ended it, `cancelled: true` for a withdrawn request); approval flows add `binding:activation-requested`, `binding:activation-approved`, and `binding:activation-denied`. Subscribe a webhook to `binding:*` to alert on elevation.

Grant `iam:bindings:activate` through a group every member belongs to (a "Member" role with `permissions: ['iam:bindings:activate']`), then make privileged roles eligible instead of standing.

### Configuration as code

The `config` API group treats a tenant's access model as a document keyed by name, so the same file can be reviewed in version control and applied to several environments:

```ts
const document = await iam.api.config.export(credential, { tenantId }); // iam:config:read
const plan = await iam.api.config.plan(credential, { tenantId, config: document, prune: true });
const result = await iam.api.config.apply(credential, { tenantId, config: document, prune: true }); // iam:config:apply
```

A document (`version: 1`) may list `resourceTypes` (tenant-defined; `actions` are verbs), `policies`, `roles` (attached `policies` by name, plus `permissions` or an inline `document`), `groups` (with `members` as emails, matched exactly when present), `bindings` (group to role, with the eligibility fields), and `packages` (access packages naming their roles, groups, and optional `autoAssign` rule). Kinds the document omits are left alone; with `prune`, items of a listed kind that the document does not name are deleted. `plan` returns every change (`create`, `update` with the differing `fields`, `delete`, `unchanged`) and writes nothing; `apply` performs them in one transaction, authorizing each change like the direct call (`iam:roles:create`, `iam:groups:update`, `iam:bindings:delete`, ...) under the caller's grant authority, so a refusal or a validation error (unknown action, a resource type still referenced by a role, an unknown member email) rolls everything back. Protected owner roles and policies, identities, their direct bindings, credentials, and webhooks are never part of the document. The apply is audited as `config:apply` with the change summary; the CLI exposes the same operations as `config-export`, `config-plan`, and `config-apply`.

Documents may also carry `agreements` (`name`, `content`, `url?`, `required?` default true, `reacceptAfterDays?`) and `invariants` (`name`, `description?`, `subject`, `action`, `resource`, `expect`, `mode?` default `monitor`, `assumeMfa?` default true), both matched by name regardless of case. An invariant's `subject` names groups and people portably: `{ "group": "Contractors" }` (the group may be created by the same document), `{ "identity": "alice@example.com" }` (the person must exist), `{ "attribute": { "name": "department", "value": "Sales" } }`, or `{ "everyone": true }`. A changed agreement `content` publishes a new version, so everyone accepts the new text; other agreement edits keep acceptances. Exports list these kinds only when the tenant has some. Enforced invariants are checked around the whole apply against the invariants as they were before it, so relaxing an invariant and making the change it forbade take two applies. Changing them needs `iam:agreements:manage` and `iam:invariants:manage`.

AI agents, models and budgets are kinds too (see [AI agents](agents.md) and [inference](inference.md)). `agents` names each agent (matched regardless of case) with its `sponsor` by email (an active person of the tenant) and its profile: `description`, `purpose`, `model`, `provider`, `url`, `protocols`, `delegable` (default true), `maxDelegatedSessionSeconds`, `boundary`, and `tokenAudiences`. A new sponsor is audited as `agent:sponsor-change`, and pruning deletes the agent (revoking its delegations). `inferenceModels` lists the tenant's own models, with their `provider` by name (providers hold sealed keys, so they are created through the API and only named here), `upstreamModel`, prices, `tier`, limits, `fallbacks`, `providerTools`, and `enabled`. `inferenceBudgets` names budgets with a `subject` of `"tenant"`, `{ "group": … }` (possibly created by the same document), `{ "identity": email }`, or `{ "agent": name }` (possibly created by the same document), plus `scope`, `period` (`minute` to `month`), and limits. The model and budget kinds need the `inference` option. API keys, provider keys, and delegations are runtime state and never synced. Changing these kinds needs `iam:agents:create|update|delete` and `iam:inference:manage`.

Approvals and denials are audited as `access-request:approve` and `access-request:deny` with the requester, roles, and resulting binding IDs in the metadata.

### Access packages

An access package bundles roles and group memberships that are granted together: an onboarding kit, a project profile, a vendor's access. `packages.create({ tenantId, name, description?, roleIds?, groupIds?, maxDurationMs?, requireJustification? })` (`iam:packages:create`; names are unique per tenant, protected roles cannot be packaged, at most 50 of each) defines one, and `packages.assign({ tenantId, packageId, identityId, expiresAt?, justification? })` grants it: every role becomes an ordinary identity binding and every group an ordinary membership, all ending at `expiresAt`, created under the caller's grant authority and tagged with the assignment. The caller needs `iam:packages:assign` on the package plus what the direct calls need (`iam:bindings:create` on each role, `iam:groups:update` on each group), so a package never widens what its assigner could grant by hand. Each role becomes a binding of the assignment's own, even when the person already holds the role another way, so a package never depends on, replaces, or removes a binding granted by hand. A group has one membership record per person: a membership that already lasts at least as long is left alone and reported in `skipped`, a shorter one is extended and becomes the assignment's, and when two packages of the same person share a group the membership belongs to whichever needs it longest and passes to the other when that one is revoked or shortened. Editing a package's binding or membership by hand (`bindings.update`, `groups.updateMember`, re-adding a lapsed member) takes the record over: revoking the package no longer removes it. An assignment whose bindings no longer grant (its assigner's authority was revoked, for example by offboarding them) is reported as `broken` and may simply be assigned or requested again. `maxDurationMs` makes an end date mandatory and caps it; `requireJustification` makes the justification mandatory. `packages.revoke({ packageId, identityId })` removes exactly the records the assignment added (it needs only `iam:packages:assign` on the package: the assignment owns those records whichever authority issued them), and an assignment ends by itself at `expiresAt` (the purge worker sweeps it together with its bindings and memberships). `packages.extend({ packageId, identityId, expiresAt | null })` moves that end for the assignment and everything it created at once (audited as `package:extend`). Shortening needs only `iam:packages:assign`; lengthening (or `null`) is granting, so it needs the same rights as `assign` plus a grant authority, and the package's bindings move to the extender's authority so the longer grant is bounded by what the extender may give. `packages.list` and `get` report live holder counts, `packages.listAssignments({ packageId?, identityId?, includeExpired? })` lists holders (`iam:packages:read`), and offboarding or deleting an identity removes its assignments. A role or group cannot be deleted while a package includes it, nor a package while someone holds it (`RESOURCE_IN_USE`); changing a package's contents affects future assignments only. Assignments are audited as `package:assign` (with the counts, the skips, and the justification) and `package:revoke`; the configuration document carries packages by name (`packages: [{ name, roles, groups, maxDurationMs?, requireJustification?, requestable?, approverGroup?, managerApproval?, autoAssign? }]`). Assignments can also be automatic; see [Automatic assignment](#automatic-assignment-birthright).

Packages can also be self-service. A `requestable` package is asked for with `packages.request({ tenantId, packageId, expiresAt?, justification? })` under `iam:packages:request` on the package, from an ordinary session, with the same end-date and justification rules as assigning; the request waits for the tenant's `approvalLifetimeMs` (one day by default, from the access policy), but never beyond the end it asks for, and the members of `approverGroupId` are emailed it (`package-request`). A request that names approvers but would reach none (an empty approver group, or `managerApproval` without an active manager) is refused with `INVALID_TRANSITION`. Tightening a package (turning `requestable` off, requiring a justification, or capping the duration) cancels the pending requests that no longer fit, with the reason as the note, and a direct `packages.assign` marks the person's pending request for the package approved. Decisions cannot be made from an impersonation session (`IMPERSONATION_RESTRICTED`), `listApprovals` lists only requests the caller holds `iam:packages:approve` on, and `listRequests` reports a lapsed request as `expired` before the purge worker marks it. `packages.approveRequest({ requestId, expiresAt?, note? })` and `denyRequest({ requestId, note? })` need `iam:packages:approve` on the package and, when the package names approvers, membership of the approver group or, with `managerApproval`, being the requester's manager (root always may); nobody decides on their own request. Approval assigns the package to the requester under the approver's authority, so the approver needs the same rights as `assign` (`iam:bindings:create` on each role, `iam:groups:update` on each group), for the end the requester asked for unless the approver chooses another; the requester is emailed either way (`package-decided`). `packages.cancelRequest` withdraws one's own pending request, `packages.listApprovals` shows an approver what awaits them, `packages.listRequests({ packageId?, identityId?, status? })` serves administrators (`iam:packages:read`), and `packages.listMine` gives a member the requestable packages with their own status on each (held, awaiting approval, or open to request) plus their assignments and recent requests. Lapsed requests are marked `expired` by the purge worker, offboarding cancels pending ones, and the flow is audited as `package:request`, `package:request-approved`, `package:request-denied`, and `package:request-cancelled`. Grant `iam:packages:request` through a group every member belongs to, as with `iam:bindings:activate`.

### Automatic assignment (birthright)

A package with a rule is given to every active identity that matches it and taken away from automatic holders that stop matching: `packages.create` or `packages.update({ ..., autoAssign: { include, exclude?, graceMs?, maxGrants?, maxRemovals? } })`.

```ts
// Everyone in engineering (people, not service accounts)
{ include: [{ StringEquals: { 'principal.kind': 'user', 'principal.department': 'engineering' } }] }
// Direct members of a group
{ include: [{ ArrayContains: { 'identity.groups': '<groupId>' }, StringEquals: { 'principal.kind': 'user' } }] }
// Every service account
{ include: [{ StringEquals: { 'principal.kind': 'service' } }] }
// A verified email domain, except contractors, and except two named people
{
  include: [{ StringEqualsIgnoreCase: { 'identity.emailDomain': 'acme.com' }, Bool: { 'identity.emailVerified': true } }],
  exclude: [{ Bool: { 'principal.contractor': true } }, { StringEquals: { 'principal.id': ['id1', 'id2'] } }],
}
```

- **The language is the policy [condition](#conditions) language.** Each clause is a condition block; include clauses are ORed, a matching exclude clause denies, and types are strict. A missing attribute never satisfies an operator, negated ones included, so test absence with `Exists: { 'principal.department': false }`. The keys are `principal.id`, `principal.kind`, `principal.owner`, and `principal.<declared attribute>` (meaning exactly what they mean in policies), plus rule-only facts: `identity.email`, `identity.emailDomain` (lower-case), `identity.emailVerified`, `identity.managerId`, and `identity.groups`, the person's group memberships that no access package created, so rules never chain onto another package or keep themselves alive (`principal.groups` is refused). The org structure keys `identity.teams` (the [teams](teams-and-departments.md) the person belongs to and every team above them) and `identity.departments` (their department and every department above it) hold IDs; a team membership that team sync copied from a group counts only while the person is in that group by a membership no package created. There are no session, request, or resource keys, no policy variables, and no IP operators; `DateBefore`/`DateAfter` apply to declared string attributes. Empty clauses are refused: "everyone" is spelled out, for example `Exists: { 'principal.id': true }`. `packages.previewAutoAssign({ tenantId, packageId?, autoAssign? })` lists the valid keys, shows what a rule matches and what a run would change, and warns when a clause does not test `principal.kind` (it then also matches service accounts) or tests an email without `identity.emailVerified` (administrator-set and SCIM-provisioned addresses are unverified).
- **Authority.** The rule's owner is whoever last set it or changed the package's roles or groups. They need everything assigning by hand needs (`iam:packages:assign`, `iam:bindings:create` on each role, `iam:groups:update` on each group, and the right to use the authorities behind the groups' bindings) and a grant authority; role sessions, session tokens and impersonation are refused. Automatic bindings are issued under the owner's grant authority, bounded by its chain, and every run re-checks the owner's status, authority, and rights before adding anything. When the owner is disabled, offboarded, or demoted, or their authority is revoked, the rule is suspended (`package:auto-suspended`): nobody new is added, people who stop matching are still removed, and bindings under a revoked authority stop granting at once. Another administrator takes over by saving the rule again; the holders' bindings are then re-issued under the new authority. Own production rules through a managed service account and configuration as code, and transfer rules before offboarding their owner.
- **When it runs.** Right after `identities.create`/`createMany`/`update`/`setStatus` and `serviceAccounts.create`/`update`, after team and department changes made through their APIs (members added, removed, re-timed, approved, or leaving; teams created, moved, re-synced, or deleted; people placed, moved, imported, or unassigned; departments moved or deleted; `departments.syncManagers`), and after a rule is saved (up to 200 changes; the response carries `reconcile`); on demand with `packages.reconcile` (console: Reconcile now); and as the scheduler job `iam.reconcilePackages()` / `better-iam reconcile`, which must be scheduled because SCIM provisioning, invitations, federated sign-in attributes, group membership changes, and expiry take effect through it. Each change is its own transaction; a second run over an unchanged directory writes nothing.
- **Removal and grace.** By default an automatic holder who stops matching loses the package at the next run. With `graceMs` (at most 90 days) the assignment and exactly its records end at a set time instead: the person gets the expiry reminder, access ends even if no run happens, matching again restores it, and the purge worker sweeps it. Only what the assignment created is removed.
- **Interplay.** Manual assignments are never touched, and `packages.assign` turns an automatic assignment into a manual one (`replacedAutomatic`). `revoke` and `extend` refuse automatic assignments while the rule exists; exclude the person in the rule instead. `maxDurationMs` cannot be combined with a rule, and `requireJustification` is satisfied with "Automatic: matches the package rule". A pending request is cancelled when the package is assigned automatically. Disabled and expired identities are frozen (never assigned or removed by a rule); offboarding and deletion remove their assignments. A separation-of-duties prevent conflict skips that identity (reported in `failed`, audited once, retried later) and never fails a run or an identity update. A record removed by hand comes back while the person matches, so certify the rule rather than the binding. Content changes update every automatic holder, while manual holders keep what they were given. Clearing the rule (`autoAssign: null`) removes the automatic holders at the next run, or keeps them as manual assignments with `keepAutomaticAssignments: true`. A package with holders cannot be deleted, and a group, team, or department a rule names cannot be deleted (`RESOURCE_IN_USE`).
- **Safety.** Unattended runs (the scheduler, and `packages.reconcile` without `confirm`) hold back more than `maxGrants` (100) new grants or `maxRemovals` (25) removals per package (`package:auto-braked`) until someone with the rights to assign the package by hand confirms: `packages.reconcile({ packageId, confirm: true })`, the console's "Confirm held changes", or `better-iam reconcile --tenant T --package P --confirm`. A save through the API pre-approves its own planned counts for a day; configuration apply does not. A rule that no longer validates (an attribute declaration removed from the deployment, a group gone) is suspended with nothing assigned or removed.
- **Configuration as code.** Documents carry `autoAssign` with group names in `identity.groups`, team slugs in `identity.teams`, and department names in `identity.departments`; omitting it leaves the rule alone and `null` removes it. Owner, revision, and approval are runtime state and never synced, and apply does not reconcile: run `better-iam reconcile` afterwards.
- **Audit.** `package:auto-rule` (set, change, owner, contents, clear) and `package:auto-confirm` carry the administrator; `package:auto-assign` (assign, refresh, restore), `package:auto-ending`, `package:auto-revoke`, `package:auto-failed`, `package:auto-suspended`, `package:auto-resumed`, and `package:auto-braked` are recorded by `deployment-operator`. Subscribe a webhook to `package:auto-*`.

## Relationships

Relationship tuples record that an identity or group stands in a named relation to one resource: _alice is an `owner` of `folder/plans`_, _the design group are `viewer`s of `folder/plans`_. They express sharing and ownership without listing resource IDs in policies. A resource type declares the relations it supports (`relations: ['viewer', 'editor', 'owner']` in `permissions.resourceTypes`, in a plugin's `resourceTypes`, or on `resourceTypes.register/update` for tenant-defined types; names are lowercase, at most 32 per type). Undeclared relations are rejected, and a relation still held by someone cannot be dropped from its type.

`iam.api.relationships.create({ tenantId, type, id, relation, subjectType, subjectId, expiresAt? })` requires `iam:relationships:create` on `iam/{type}/{id}`. Managed resources must be registered; application-owned resources are accepted as named. `list` (filters `type`, `id`, `relation`, `subjectType`, `subjectId`; `includeExpired`) requires `iam:relationships:read` on `iam/{type}/{id}`, `iam/{type}/*`, or `iam/*`, and `delete` requires `iam:relationships:delete` on the tuple's resource. Tuples are removed with their identity, group, or managed resource. Role sessions hold no relations.

During evaluation the principal's live relations on the evaluated resource, held directly or through group membership, appear as `resource.relations` (a sorted string array) and those on its registered parent as `resource.parentRelations`, so a role can say:

```ts
{ effect: 'allow', actions: ['files:read'], resources: ['file/*'],
  conditions: { ArrayContains: { 'resource.parentRelations': ['viewer', 'editor', 'owner'] } } }
```

For administrative actions on `iam/{type}/{id}` naming a registered managed resource, `resource.relations`, `resource.parentRelations`, `resource.ownerId`, `resource.parentId`, and the registered attributes describe that resource. This is what lets an `owner` share a folder (`iam:relationships:create` conditioned on `resource.relations`) without holding a tenant-wide administrative role. Reverse queries (`listAccessible`) see relationships too.

## Conditions

Supported operators: `StringEquals`, `StringNotEquals`, `StringEqualsIgnoreCase`, `StringNotEqualsIgnoreCase`, `StringLike`, `StringNotLike`, `StringLikeIgnoreCase`, `Bool`, `NumericEquals`, `NumericNotEquals`, `NumericLessThan`, `NumericLessThanEquals`, `NumericGreaterThan`, `NumericGreaterThanEquals`, `DateBefore`, `DateAfter`, `IpAddress`, `NotIpAddress`, `ArrayContains`, `ArrayContainsAll`, and `Exists`.

Conditions AND operators and keys; multiple expected values use OR, except that negated operators (`*NotEquals`, `StringNotLike`, `NotIpAddress`) and `ArrayContainsAll` must hold for every listed value. Types are strict: a missing or wrongly typed context value never satisfies an operator, including the negated ones, so `StringNotEquals` on an absent key is false rather than vacuously true. `ArrayContains` matches when the context array contains any listed value; `ArrayContainsAll` when it contains all of them. IP rules support IPv4/IPv6 CIDR. Invalid syntax and unknown operators are rejected at policy creation/update.

Trusted built-in context includes `principal.id`, `principal.tenantId`, `principal.mfa`, `principal.kind` (`user` or `service`), `principal.owner`, `principal.rootAdmin`, `principal.sessionKind`, `principal.authMethod` (`password`, `passwordless-email`, `passwordless-sms`, `passkey`, `federated`, or `impersonation`; absent for API keys, role sessions, session tokens, and sessions issued before methods were recorded), `principal.impersonated` (true while an administrator acts as the member) with `principal.impersonatorId`, `principal.groups` (group IDs), `principal.roles` (role IDs bound directly or through groups), `principal.agreements` (names of [terms of use](#terms-of-use) accepted in their current version) and `principal.pendingAgreements` (required ones still owed), `principal.onboarding` (names of [onboarding flows](onboarding.md) completed) and `principal.pendingOnboarding` (required ones still open; both read only when a condition names them), `resource.tenantId`, `resource.relations`, `resource.parentRelations`, and `request.time`. Attributes declared in `permissions.identityAttributes` and set with `identities.update` or `serviceAccounts.update` appear as `principal.{name}`; they cannot shadow the built-in principal keys. Resolver and registry attributes appear as `resource.{name}`; managed resources additionally expose `resource.ownerId`, `resource.parentId`, and `resource.parentType` when set. `resolveContext` (on the server options or on a plugin) can add server-derived values; server-derived principal and request keys always win over them. Neither function may trust arbitrary browser attributes.

Policy updates require the current version and retain previous versions (`policies.listVersions`); `policies.restoreVersion` rolls back to an earlier document as a new version after re-validating it against the catalog. `policies.test` evaluates a candidate document that is not stored against an action, a resource string, and a caller-supplied context (`iam:policies:simulate`), for policy editors. Public authorization responses omit matched statements; the administrator-only simulation API can explain policy results. Simulation does not create a session or grant access.

### Feature flag context

`tenant.features` lists the keys of every [feature flag](feature-flags.md) that is on for the decision's tenant, sorted, with internal flags included. Use it to gate actions on a flag, for example `{ "ArrayContains": { "tenant.features": "exports" } }`. The server reads flags only for decisions whose documents name the key, and it removes any `tenant.features` value that `resolveContext` or a plugin supplies. `policies.test` fills it with the tenant's current flags unless the context passes it. Policy lint treats it as a list, so use `ArrayContains` rather than string operators.

### Team and department context

`principal.teams` lists the IDs of the [teams](teams-and-departments.md) the person belongs to directly and of every team above them, `principal.departments` the ID of their department and of every department above it, and `principal.departmentId` their own department (absent without one). They describe people in their own organization (assumed roles see empty lists) and are read only when a document names them. For example `{ "ArrayContains": { "principal.departments": ["<engineering id>"] } }` admits everyone in Engineering and its sub-departments, and `{ "StringEquals": { "principal.departmentId": "${resource.departmentId}" } }` limits an action to resources of the person's own department. Identity attributes cannot use the names `teams`, `departments`, or `departmentId`.

### Spend context

`principal.spendExceeded` is true when an enforced [spend budget](billing.md#spend-in-policies) covering the principal in the decision's tenant is spent, and `principal.budgetsExceeded` lists the names of every spent budget that covers them (tenant budgets up the tree and, for a person of the tenant, their own, their teams' and their department's; assumed roles see only the tenant's). They are read only when a document names them, from budget standings cached for up to 30 seconds. `{ "Bool": { "principal.spendExceeded": true } }` in a deny statement stops costly actions once the money is gone. Identity attributes cannot use the names `spendExceeded` or `budgetsExceeded`.

### Session context keys

Every decision also carries keys that describe the credential rather than the identity. The server owns them: after `resolveContext` and plugin context are merged, every server key (all of the principal keys above, `request.time`, the keys below, and the whole `principal.sessionTags.` family) is deleted before the server assigns its own values, so neither your application nor a plugin can supply one, even for a credential where the server leaves it absent. Their bare names are reserved: declaring an identity attribute called `sessionId`, `tokenIssueTime`, `authTime`, `mfaTime`, `sourceTenantId`, `sessionName`, `sourceIdentity`, `sessionTags`, `sessionTagKeys`, `webIdentityProvider` or `webIdentitySubject` fails with `INVALID_CONFIG`. Timestamps are ISO-8601 strings, so compare them with `DateBefore` / `DateAfter`.

| Key                             | Type                                       | Present                                                                                                                                                                                              | AWS analogue                         |
| ------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `principal.sessionId`           | identifier                                 | Always (`simulation` for simulated principals)                                                                                                                                                       | session part of `aws:userid`         |
| `principal.sessionKind`         | `user`, `role`, `api-key`, `session-token` | Always                                                                                                                                                                                               | `aws:PrincipalType`                  |
| `principal.tokenIssueTime`      | timestamp                                  | Always: when the session was created                                                                                                                                                                 | `aws:TokenIssueTime`                 |
| `principal.authTime`            | timestamp                                  | Always: sign-in time; role sessions and session tokens copy their source's, API keys use their creation, web identity the exchange time                                                              | OIDC `auth_time`                     |
| `principal.mfaTime`             | timestamp                                  | After a first-hand MFA or passkey ceremony, a session-token `mfaCode` step-up, or copied from such a source; absent for API keys, remembered devices, impersonation, web identity and older sessions | `aws:MultiFactorAuthAge` (absolute)  |
| `principal.sessionTagKeys`      | list                                       | Always (`[]` without tags), sorted                                                                                                                                                                   | `aws:PrincipalTagKeys`               |
| `principal.sessionTags.<key>`   | string                                     | Role sessions with tags (from `roles.assume` tags or a web trust's `tagClaims`); keys are matched case-sensitively                                                                                   | `aws:PrincipalTag/<key>`             |
| `principal.sourceTenantId`      | identifier                                 | Classic role sessions                                                                                                                                                                                | `aws:PrincipalAccount` of the source |
| `principal.sessionName`         | identifier                                 | Role sessions and session tokens when named (always for web identity)                                                                                                                                | `sts:RoleSessionName`                |
| `principal.sourceIdentity`      | identifier                                 | Role sessions whose trust admits or maps a source identity                                                                                                                                           | `aws:SourceIdentity`                 |
| `principal.webIdentityProvider` | identifier                                 | Web-identity role sessions (the OIDC provider id)                                                                                                                                                    | `aws:FederatedProvider`              |
| `principal.webIdentitySubject`  | string                                     | Web-identity role sessions (the verified external `sub`)                                                                                                                                             | `<provider>:sub`                     |
| `request.sourceIp`              | identifier (use `IpAddress`)               | When the request runs in a client scope with a parseable IP (`http.clientInfo`, framework headers, `auth.withClient`); never in simulations                                                          | `aws:SourceIp`                       |

`request.ip` keeps its application-supplied meaning; `request.sourceIp` is the address the server itself saw. Package rules are evaluated without a session, so they refuse the session keys and the `principal.sessionTags.` family. `policies.test` defaults `principal.sessionId` to `simulation`, `principal.tokenIssueTime` and `principal.authTime` to now, and `principal.sessionTagKeys` to `[]`; pass them in the context to test other values. For role sessions whose trust sets `passSourceAttributes: false`, identity attributes (`principal.{name}`) are not copied; session tags are the supported channel instead.

Recipes:

```ts
// Revoke everything issued before an incident, as policy (AWS "revoke older sessions"), without touching rows.
{ sid: 'RevokeOlder', effect: 'deny', actions: ['*'], resources: ['*'],
  conditions: { DateBefore: { 'principal.tokenIssueTime': '2026-09-22T12:00:00Z' } } }

// Allow only from the office network. Prefer allow-style IpAddress: request.sourceIp is absent for in-process calls
// without a client scope, and a missing key never satisfies an operator, so a Deny with NotIpAddress would do nothing.
{ effect: 'allow', actions: ['payroll:*'], resources: ['*'],
  conditions: { IpAddress: { 'request.sourceIp': ['203.0.113.0/24', '2001:db8::/32'] } } }

// Require an MFA ceremony after a cutoff, e.g. after everyone re-enrolled (absolute form of aws:MultiFactorAuthAge;
// Date operators take literal times, not variables). API keys and password-only sessions have no mfaTime, so they fail.
{ effect: 'allow', actions: ['billing:refund'], resources: ['*'],
  conditions: { DateAfter: { 'principal.mfaTime': '2026-09-01T00:00:00Z' } } }

// ABAC on a session tag set at roles.assume (the trust must list `project` in allowedTagKeys).
{ effect: 'allow', actions: ['documents:read'], resources: ['*'],
  conditions: { StringEquals: { 'resource.project': '${principal.sessionTags.project}' } } }

// Only the production deploy workflow's web-identity sessions may deploy.
{ effect: 'allow', actions: ['deployments:create'], resources: ['*'],
  conditions: { StringEquals: { 'principal.webIdentitySubject': 'repo:acme/app:environment:production' } } }
```

## Temporary roles and service credentials

Platform administrators establish exact source-identity/target-role trust. Assumption also requires the source identity's `iam:roles:assume` permission for `iam/{targetRoleId}`. Trust may require MFA and an external ID. Role sessions default to 15 minutes, cannot exceed the trust's `maxSessionSeconds` (an hour unless set), the deployment's `sts.maxRoleSessionSeconds` (an hour unless configured, at most 12 hours), or the source credential expiry, and cannot chain.

The source may be a person's own session, an API key, or a session token from `sts.getSessionToken` (which is the same identity with the same or fewer grants, not chaining); a role session as the source is `ROLE_CHAINING_DISABLED`, and the live `iam:roles:assume` decision runs as the verified source, so a session token's policy and its source's scopes bound what it may assume, though not what the resulting role session may do (the role, the trust `ceiling` and the session `policy` bound that). A trust with `requireMfa` needs an MFA source: a person's MFA session, or a session token minted with `mfaCode`. Root sets per-trust `allowedTagKeys` (session tags, `principal.sessionTags.<key>`) and `sourceIdentityMode` (`principal.sourceIdentity`); both are closed by default because the caller chooses their values. `passSourceAttributes` controls whether the source identity's attributes reach the role session as `principal.{name}`: new cross-tenant trusts default to `false`, same-tenant trusts to `true`, and older trusts keep passing them until `trust.update` changes it. Web-identity trusts replace the named source with a verified OIDC token matched by claim conditions over `token.<claim>` keys; see [temporary credentials](temporary-credentials.md#web-identity-federation). Every temporary credential fails `requireRecent`, so it cannot perform operations that need recent authentication.

Target-role policies replace source application permissions; target and session boundaries still constrain them. Revoking source credentials, trust, identities, or relevant grant authority invalidates dependent access. API keys are opaque credentials for service identities, default to 90-day expiry, and retain their issuing authority ceiling. Rotation invalidates the old key transactionally.

The policy format is Better IAM's versioned format, inspired by [AWS's policy evaluation concepts](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html). It is not an AWS JSON-policy parser.
